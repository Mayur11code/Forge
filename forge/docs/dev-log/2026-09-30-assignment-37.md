## I6, and why it is not I1

`triggerWorkflowRun` (`workflow-run.ts:5`) performs no authentication and no
organization check. `startWorkflow` (`execution/trigger.ts:8`) then loads the
workflow with `findUnique({ where: { id: workflowId } })` and no `orgId`. Any
authenticated user can start any tenant's workflow and seed an attacker-chosen
`triggerPayload` into the run context, where `{{trigger.outputs.*}}` resolves it
into step inputs.

It is a **different defect from I1 on a different path**, and closing I1 does
not reduce it. I1 was cross-tenant *update*; I6 is cross-tenant *execution*. The
consequence is not that a blueprint gets overwritten but that a real run starts
on someone else's automation with attacker-chosen data. Phase 0 did not see it,
so `assignments-37-phase-0-audit.md` is deliberately **unmodified** and still
describes only what Phase 0 saw; I6 lives in the register with its own
provenance note. The `test-run` route
(`api/workflow/test/[workflowId]/test-run/route.ts`) is a second reachable caller
and is named in the ticket, because a fix that only patches the server action
would leave the primitive reachable.

Gate G: 37.12 cannot become `VERIFIED` while I6 is open.

## 37.0A — I1, tenant-scoped workflow update

The write was `db.workflow.update({ where: { id: workflowId } })`. `getOrgAccess`
ran first and proved the caller belonged to *an* organization, and the predicate
that followed never mentioned it. Any authenticated member of any org could
overwrite any workflow by id — graph, `eventId`, and the `isActive` flag that
decides whether that tenant's automation fires.

The route segment is named `[orgId]` but carries an organization **slug**
(`router/page.tsx:38` seeds URLs with the slug), so `getOrgAccess` is live here
and the defect was reachable rather than masked by a broken route. Worth
checking before assuming a confusingly named param hides a bug.

### The two requirements did not fit in one query

The ticket asked for two things that pull against each other:

- the actual database operation must enforce tenant ownership, with `orgId` in
  the write predicate;
- a cross-tenant attempt must issue **no write at all**.

`updateMany({ where: { id, orgId } })` satisfies the first and still invokes a
write on a cross-org attempt, so a test asserting "the update was not called"
fails against it. `findFirst` followed by an unscoped `update` refuses cleanly but
leaves an unscoped write predicate. And the obvious repair — `update({ where: {
id, orgId } })` — does not typecheck, because this action imports the **raw**
client from `@/lib/prisma/db` where the unique input is `id` alone. `orgId` is
indexed but not unique.

So: a tenant-scoped `findFirst` that refuses before any write, then a
tenant-scoped `updateMany` as the write. The authorizing read and the mutation
are constrained independently, so they cannot disagree, and there is no window
between them. This matches the engine's existing convention — `wrapper.ts` and
`state.ts` both claim rows via `updateMany` with a multi-field predicate.

A foreign workflow and a nonexistent one return the **same** message, following
the existing `updateTaskInOrg` precedent (`update-task.ts:71-77`). Distinct
wording would make the endpoint an existence oracle for other tenants' workflow
ids. The test compares the two responses with `toEqual` rather than asserting
each string, so a future divergence fails the suite.

## 37.0B — I2, node validation at the persistence boundary

`IncomingNodeSchema.data` was `.optional().or(z.any())`. `z.any()` accepts every
value including `undefined`, so the union's right-hand branch always won and the
left-hand branch was never reached: `eventId`, `actionType`, `config` and
`isCritical` — everything that decides what executes — crossed the boundary
unchecked. The update path was blunter, validating `z.array(z.any())`, an array
literal that accepts any element and therefore any input at all.

### The schema and the application disagreed about where the discriminator lived

The obvious fix — delete `.or(z.any())` — would have made the union reachable
and **rejected every node this application creates.** The union was keyed on
`data.type`, but React Flow carries the discriminator on the node, and
`WorkflowCanvas.tsx:150-162` never sets `data.type`:

```ts
{ id, type: 'trigger', position, data: { label: 'New Trigger', eventId: null } }
```

`AppNode`'s inferred data type has no `type` field either, so the schema and the
type it was written against had been disagreeing the whole time. Nothing had
caught it precisely *because* the `z.any()` branch swallowed every value.

The union is now keyed on `node.type`, which also makes the node's type and its
data structurally incapable of disagreeing — a node typed `trigger` must carry
`eventId` — with no cross-field refinement needed to notice when it does not.
Confirmed against the caller and with a standalone Zod script before the fix
landed, rather than after.

Both actions now compile and persist the **parsed** nodes rather than the raw
argument. Validating a copy while persisting the input would leave unvalidated
keys in the row and keep the check advisory, which is the same criticism the
register makes of ProposalSchema in 37.2. Unknown keys are stripped rather than
refused: the schemas are ordinary Zod objects, and `.strict()` would turn any
field added to the canvas later into a hard save failure. Stripping already
guarantees the database and the compiled definition contain only schema-approved
fields.

## What the tests had to be built around

Both suites are only meaningful because of two decisions in the shared prisma
double (`src/tests/workflow/helpers/prisma-double.ts`).

**The double has to enforce the constraint it exists to test.** The new
`workflow` delegate's `findFirst` and `updateMany` share one
`matchesWorkflowWhere` that actually filters `orgId`. A permissive double would
have let the cross-org case pass because the test forced a result, rather than
because the query excludes the row. Dropping the filter now fails loudly, which
is the correct outcome. The file's header already argued this point about
`updateMany` compare-and-sets; the same reasoning applies to a tenant predicate.

**Both regression suites were mutation-checked.** A test that passes against the
fix *and* the bug is not evidence of anything, so each was re-run against a
deliberately reverted vulnerable version:

| Suite | Reverted to | Result |
| --- | --- | --- |
| `workflow-update-scope.test.ts` | unscoped `where: { id: workflowId }` | **3 of 5 failed** — the cross-org case returned `{ success: true }` and overwrote the foreign row |
| `workflow-node-validation.test.ts` | `.optional().or(z.any())`, `z.array(z.any())` on update | **19 of 23 failed** |

The I2 suite holds the real canvas payload verbatim rather than a tidied-up
approximation, so a future change that breaks actual saves fails the tests.

## One test expectation that was wrong, and one fixture that had to change

Worth recording because both were caught by running the suites rather than by
reading them.

A stray `eventId` on an **action** node is accepted and stripped, not rejected —
`ActionNodeDataSchema` is not strict. My first version of the test asserted
rejection and failed. The code was right and the expectation was wrong; the
asymmetry (a trigger node missing `eventId` *is* rejected, because it loses a
required field) is now pinned by a named test so it reads as deliberate rather
than as a hole.

The 37.0A fixture node omitted `label`. The moment 37.0B made validation real,
those tenant-scope cases began returning `"Malformed workflow data."` **before
reaching the tenant check** — they would have passed for entirely the wrong
reason while still being green. The fixture was made a valid node so it exercises
tenant scope, and node-shape rejection moved to the 37.0B suite. Two suites
passing simultaneously is not the same as one suite passing for the right reason.

## Deliberately left open

**I6 is untouched.** No execution-path file was modified — `workflow-run.ts`,
`execution/trigger.ts` and `execution/resolver.ts` have an empty diff. It remains
a separate P0 and still gates 37.12.

**`uiEdges` is still unvalidated.** I2's scope named the node schema and the
update path only. Edges carry no data payload and the compiler reads only
`edge.source` / `edge.target`, so an unvalidated edge cannot introduce node data.
Reference and data-dependency validation is F6 and belongs to 37.3.

**Rows written under the permissive schema will now fail to re-save** rather than
silently persisting again. That is the intended direction, and no migration is
proposed: 37.0B is a Zod fix, and rewriting stored `uiNodes` is F1's 37.10/37.11
concern.

**The lint errors were not fixed.** They are pre-existing on the action
signatures, outside both tickets' scope, and confirmed present at HEAD.

## Still not verified

All evidence above is Jest-level against an in-memory prisma double. **No live
database, queue, Gemini, or real workflow execution has been exercised.** In
particular there is no live two-tenant check of the I1 predicate, and no
round-trip of a workflow edited through the actual canvas UI. Phase 37.16 remains
the phase that owes both, and the tracker records this rather than letting a green
suite imply more than it proves.
