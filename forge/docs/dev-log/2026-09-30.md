## The defect

Topic B. The self-healing loop could not actually heal.

Every tool reported a schema rejection as `parsed.error.issues[0]?.message` —
the first issue, with no field name. A model that sent `limit: "many"` to
`listTasks`, which has four optional fields, was told:

```
Invalid input: expected number, received string
```

It cannot tell which field is wrong, so the only ways forward are to guess or to
resend the same call. And the prompt said only *"report the returned error
honestly and do not retry blindly"* — which points at surfacing the complaint to
the user rather than fixing it, and collides with the prompt's own rule against
revealing internal implementation detail.

Both halves were wrong in the same direction, so neither was a finding on its
own. The observation was not machine-readable, and the prompt had no rule that
made it actionable.

### Fix

`buildValidationFailure` in `forge/src/lib/ai/agent/tools/shared-output.ts`,
shared by all three tools. Every issue is returned with a dotted `path` and the
schema's own `code`; the list is capped at 8 and the count of anything dropped is
stated, so a truncated list is never mistaken for a complete one; the field name
also appears in the human-readable `error` line.

`AGENT_PROMPT_VERSION` is now `v3`. Its `<TOOL_CONTRACT>` states that
`INVALID_INPUT` is feedback on the model's own arguments, that the named field
is what to fix, and that two identical rejections mean stopping and asking the
user.

No value from the submitted input is echoed. Zod's `unrecognized_keys` message
names offending *keys* — which the model itself just wrote — and never their
values, so an injected `orgId` or a hallucinated credential cannot be reflected
back into the transcript. Asserted directly in a test.

## What was checked and deliberately left alone

**`getMessages` ordering.** `orderBy: { createdAt: "asc" }` with no tie-breaker
is not a total order in SQL, so it was worth checking rather than assuming. It
is not a defect. All three `createMessage(..., tx)` call sites write exactly one
message per transaction, so no two messages that must stay in relative order can
share a timestamp; the pair that matters — an assistant tool-call and the tool
result answering it — is always separated by a queue delivery, hence a
transaction boundary. The only remaining tie window is several assistant
messages from one turn, which share a role and a `step`. A secondary `id`
tie-breaker would make the query formally deterministic but would guard a case
with no demonstrated failure.

**A separate circuit breaker.** `MAX_AGENT_STEPS = 5` and every continuation
claims a new step, so a model retrying bad arguments is already bounded at five
model calls. A second layer over a cap that exists is not a fix.

**`message-mapper.ts` persisting JSON without validating it.** Known, planned
Phase 5 work. Out of scope here, and the brief was explicit that it is not to be
turned into speculative architecture work.
