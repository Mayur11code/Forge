# 2026-10-21 — Phase 37.14: Self-healing observations (three-loop separation)

**Status: IMPLEMENTED — not VERIFIED.** The phase's verification gate is an
integration test exercising each of the three loops separately; that test exists
and drives the real production services against the shared prisma double. It is
**mocked coverage**: no real-Postgres exercise of the wait compare-and-set and no
live model call. Real-PG materialization remains 37.11's open gate.

## What the phase required

Make structured validation failures drive model correction through the **existing**
agent loop, and keep three loops explicitly distinct — with **no second retry
controller** and no unbounded correction. The three loops:

| # | Loop | Trigger | Resolver | Authoritative record |
|---|---|---|---|---|
| 1 | Self-correction | Structured validation issue (`INVALID_INPUT`) | Model | result + `AGENT_LOOP_REQUESTED` |
| 2 | Human clarification | `NEEDS_USER_INPUT` | Human | `proposalState = NEEDS_CLARIFICATION` |
| 3 | Human approval | `PENDING_CONFIRMATION` | Human | execution `PENDING_CONFIRMATION` / `AWAITING_APPROVAL` |

## Finding: most of the phase was already implemented

A read-only audit before touching code found that loops 1 and the durable records
for 2 and 3 were already delivered by 37.5 / 37.6 / 37.8:

- `tools/generate-workflow/execute.ts` already returns structured `INVALID_INPUT`
  issues (loop 1's correction signal), and `tool-worker.ts:271` already records
  `AGENT_LOOP_REQUESTED` for every non-clarification, non-parked completion in the
  **same transaction** as the result compare-and-set (with the outcome CAS running
  first, so duplicates short-circuit).
- The clarification and proposal records already carried distinct durable states.

So the phase's deliverable "Observation wiring — path **UNKNOWN**" was a stale
tracker entry, not a real gap. The only thing that genuinely gated 37.14 was
**AD-P7**: whether a durable pause may use the unused session-status enum slot.
Loop 2 had no session-level representation (recorded as issue I3).

## AD-P7 — resolved (owner, this pass)

**Yes.** `AgentSessionStatus.WAITING_CONFIRMATION` is now the session-level
human-wait marker. The distinct clarification/approval outcomes are preserved
*below* the session status (loop 2 = `NEEDS_USER_INPUT` result; loop 3 =
`PENDING_CONFIRMATION` execution / proposal state). No new state machine, retry
controller, queue runner, lock protocol or schema model was introduced; the enum
value already existed and no migration is needed.

### Park / clear symmetry

Park is `RUNNING → WAITING_CONFIRMATION`. All four resolutions — clarification
answer, approval, decline, and expiry — clear back to **`RUNNING`**, the symmetric
inverse of the park. The only alternative weighed was a terminal `COMPLETED`; it
was rejected because the phase does not require it and it would prejudge 37.11
materialization semantics. This choice is flagged for the owner in the tracker.

Only two transitions actually need the session to be `RUNNING` to continue: the
loop runner does not gate on session status, but `claimNextAgentStep` does — so a
continuation must restore `RUNNING` before dispatch. Clearing to `RUNNING` is
therefore not cosmetic; it is what makes the clarification answer resume the loop.

### Proposal-review expiry while parked (verified this pass)

The read-only review's suspicion was **partially confirmed**:

- **Discovery was already correct.** `findDueProposalReviewCandidates` selects
  `AWAITING_APPROVAL + expiresAt <= now` with **no session-status predicate**, so
  a due proposal on a `WAITING_CONFIRMATION` session was already a candidate.
  Expiry never depended on the stalled-session scan, and
  `redriveStalledSessions` was not touched.
- **Isolation was missing.** After a successful CAS the sweep called
  `clearAgentSessionWaiting` unconditionally. Because the session-level marker
  is coarse (it does not record *which* human act is pending), that could release
  a session still waiting on a clarification or a tool confirmation.

The correction keeps the candidate query unchanged and makes the wait release
conditional inside the **same transaction** as the CAS. It counts other
authoritative human waits for the session, excluding the row just expired:
`NEEDS_CLARIFICATION`, `AWAITING_CRITICALITY`, `AWAITING_APPROVAL`, and
`AgentToolExecutionStatus.PENDING_CONFIRMATION`. Only a zero count clears
`WAITING_CONFIRMATION → RUNNING`. The expiry itself is unchanged: no
`AGENT_LOOP_REQUESTED`, no transcript write, no materialization, no approval or
execution, and a terminal session is never resurrected (the clear CAS only
matches `WAITING_CONFIRMATION`).

Lifecycle, before → after:

| Situation | Before | After |
|---|---|---|
| Expired proposal + `WAITING_CONFIRMATION` (proposal is the only wait) | `EXPIRED`; session → `RUNNING` | unchanged |
| Future-dated proposal + `WAITING_CONFIRMATION` | untouched | unchanged |
| Expired proposal + pending clarification | `EXPIRED`; wait cleared (wrong) | `EXPIRED`; wait **kept** |
| Expired proposal + `PENDING_CONFIRMATION` tool | `EXPIRED`; wait cleared (wrong) | `EXPIRED`; wait **kept** |
| CAS loses to a human decision | no clear | unchanged |
| Terminal session + expired proposal | `EXPIRED`; status untouched | unchanged |
| `RUNNING` session (legacy) + expired proposal | `EXPIRED`; stays `RUNNING` | unchanged |

Regression coverage lives in `proposal-review-expiry.test.ts` (10 new cases).

## New suites

### `src/tests/agent/three-loop-separation.test.ts` (6 tests)

Exercises the real worker, clarification service, proposal-decision service and the
session-lifecycle CAS against the shared prisma double.

- **Case A — self-correction.** A structured `INVALID_INPUT` completion records
  exactly one `AGENT_LOOP_REQUESTED` and leaves the session `RUNNING` (never
  `WAITING_CONFIRMATION`); the execution is `COMPLETED`; no workflow was started
  (the correction path is the agent loop, not the workflow executor).
- **Case B — clarification.** A `NEEDS_USER_INPUT` completion parks the session
  `WAITING_CONFIRMATION` and records **no** loop event; the durable result carries
  `NEEDS_USER_INPUT` / `NEEDS_CLARIFICATION`, distinguishing it from approval. An
  accepted answer clears the wait to `RUNNING` and records exactly one
  continuation (idempotent on a duplicate).
- **Case C — approval.** A valid proposal parks the session `WAITING_CONFIRMATION`
  beside `AWAITING_CRITICALITY` with a revision, recording no loop event; approving
  it (against the stored fingerprint/revision) clears the wait to `RUNNING`,
  records **no** loop event, and starts no workflow.

### `src/tests/agent/no-second-retry-controller.test.ts` (8 tests)

- Boundedness at the source: `decideStepGate` runs exactly `MAX_AGENT_STEPS` turns
  and stops the next; a re-proposal claims the next step through the same gate, so
  a self-correcting session cannot exceed the budget; the over-budget decision is
  terminal with no third "retry" state.
- Single-controller property: a source scan of `src/lib/ai/agent` finds no
  retry-controller symbol, and "attempt" accounting is confined to `outbox.ts`
  (delivery retry) and `reaper.ts` (stalled-session re-drive cap) plus
  `constants.ts` (the tunables). Neither re-drives a *model turn*.
- Session-status transitions do not create a new loop: parking/clearing is
  idempotent status CAS, is a no-op when already in the target state, and never
  manufactures an outbox event.

## Honest limitations

- The wait compare-and-set is proven against the prisma double, not real
  Postgres; the double does model `updateMany` with `status` predicates and `{ in: }`,
  so the CAS logic is exercised, but rollback/isolation semantics are not. The
  expiry + wait-clear transaction is enclosure-only: a thrown error does not roll
  the in-memory writes back, so real rollback is **unverified**.
- `expireStaleProposalReviews` does not take the session lock (unchanged from
  37.9), so a worker parking the session concurrently with the expiry commit is
  not serialised. The guard reads competing waits in the expiry transaction, but
  true cross-transaction isolation cannot be demonstrated with the current
  harness.
- No live model call: loop 1's *boundedness* is proven at the gate, and *that the
  model corrects* on the structured issue is a 37.16 capstone concern.
- The parked-to-`RUNNING` vs parked-to-`COMPLETED` choice is a deliberate design
  decision flagged to the owner, not a proven requirement.
