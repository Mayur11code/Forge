# 2026-10-12 — Phase 37.4: the proposal compiler, and closing F5

37.2 made the model produce JSON that *is* a graph shape. 37.3 made it produce a
graph that *hangs together*. 37.4 is where those two become an actual boundary: one
deterministic function from an untrusted artifact to either a candidate
`WorkflowDefinition` or a structured list of `ProposalIssue`s. No executor, no I/O,
no clock.

`src/lib/workflow-types/workflow-proposal-compiler.ts` and its 25-test suite,
commits `0a87514` (compiler), `16fb9f3` (tests), `dcc49c4` (docs).

## The shape of the boundary

The word "compiler" is doing real work. A compiler is a total function with a
fixed stage order, and this one is exactly that:

```text
1. validateWorkflowProposal        structure, bounds, action membership, inputs
2. validateProposalReferences      reference + data-dependency integrity
3. mapProposalToDefinition         pure, total proposal -> definition
4. collectWorkflowDefinitionIssues existing graph-semantic rules
5. toProposalIssues                normalise collector issues -> ProposalIssue
```

Two decisions inside that are load-bearing.

**Short-circuit, always.** A failure at stage 1, 2, or 4 returns immediately. A
test pins the important case: a proposal carrying both a dangling reference *and* a
dependency cycle returns only the reference issue and no `CYCLE`. A caller must
never be shown a downstream symptom of an upstream error, because the self-correction
loop (37.14) will act on whatever it is told — telling it "you have a cycle" when the
real problem is an unknown reference sends it to fix the wrong thing.

```text
   input
     |
     v
 [1] validateWorkflowProposal ---- fail --> ProposalIssue[] (structural)
     | pass
     v
 [2] validateProposalReferences --- fail --> ProposalIssue[]
     |
     v
   [3] map (cannot fail)
      |
      v
   4. collectWorkflowDefinitionIssues -- issues --> normalize -> ProposalIssue[]
      |
      v
   success: { proposal, definition }
```

## The mapping is pure and honest

`mapProposalToDefinition` has one rule per field, and every rule refuses to invent
anything:

- step id = the record key (`localRef`); the proposal's step map *is* the identity,
  so key and inner id are identical by construction;
- `inputs` → `config` (copied, so the returned definition never aliases the input);
- `dependsOn` is copied, never inferred or repaired;
- every step is `kind: "ACTION"` — a proposal has no trigger node, and the trigger
  is a runtime namespace, not a step, so nothing is synthesized;
- `isCritical: false` provisionally — the human decision is not 37.4's to guess;
- `routingConditions` is not emitted, because a proposal cannot express it.

The interesting decision is identity. The canvas compiler stamps
`id: compiled_${Date.now()}` on every save — a value that is not read anywhere (the
engine resolves by step key; `WorkflowRun.workflowId` is the execution identity) but
that a deterministic compiler must not reproduce. It cannot use a clock, and a
proposal may not name backend identity (AD-10). So the definition `id`/`name` are
documented constants — `"proposal"` and `"Compiled Execution Graph"` (matching the
canvas compiler's own constant name). A test proves the id is constant across two
compilations and reads the module source from disk to assert the string `Date.now`
is not in it. Real identity is 37.11's job (F2/AD-P6).

## Structured output: `code` and `path`, and what `path` means

The phase's reason to exist (with F5) is that expected failures arrive as typed
issues, not prose. Phase 0 found the current path flattens them:
`describeCompileFailure` joins issue messages into one string
(`app/actions/workflows/workflow.ts:22-28`), so the caller cannot branch on a code.

The new adapter mirrors the collector's vocabulary one-for-one rather than
translating it. `ProposalIssueCode` is extended with the collector's seven members,
which makes `WorkflowDefinitionIssueCode` a subset of `ProposalIssueCode` and the
adapter *total*. Codes and messages pass through unchanged.

`ProposalIssue.path` always denotes a location in the proposal **input** — it is not
a graph path, and this phase refuses to overload it. The collector's cycle sequence
(`["a","b","a"]`) survives in the issue `message`, the way the collector already
formats it, and `path` for any cycle is simply `"steps"`. A test asserts every
normalized path is a string.

## The exhaustive switch is the safety net

`locationForGraphIssue` switches over every collector code and ends in a `never`
guard. Only **three** codes are reachable through a proposal —
`UNKNOWN_DEPENDENCY`, `SELF_DEPENDENCY`, `CYCLE` — and the other four are
unreachable by construction:

- `EMPTY_GRAPH`: an empty proposal is rejected at stage 1 as `EMPTY_PROPOSAL`
  (`workflow-proposal.ts:177-187`), so the collector never sees an empty graph.
- `ID_MISMATCH` / `DUPLICATE_STEP_ID`: steps are a record keyed by `localRef`, so
  key equals id by construction and duplicates are unrepresentable (AD-08).
- `UNKNOWN_ROUTING_CONDITION`: a proposal cannot express `routingConditions`.

The tracker's original Test Gate said "all seven existing DAG checks reachable from
a proposal". That is false, and the assignment says so. It was corrected rather than
satisfied with a fake: the phase asserts the three reachable checks end-to-end, and
asserts the adapter total over all seven so a future collector code becomes a
compile error, not a silent drop.

## F5 and AD-P4: the gate question, and a premise that was wrong

F5 asked which graph-semantic gate is canonical: `WorkflowDefinitionSchema` or
`collectWorkflowDefinitionIssues`. Phase 0's rationale included "the schema is never
called in production". That premise is now outdated — the 2026-10-01 lint pass made
the evaluator re-parse the persisted definition with
`WorkflowDefinitionSchema.safeParse(run.workflow.definition)` (`evaluator.ts:223`).

But invocation was never the deciding factor. The schema's `superRefine` re-emits
every issue as `z.ZodIssueCode.custom` and discards the cycle `path`
(`workflow.ts:243-250`) — it cannot serve a caller that needs the semantic `code`.
So **AD-P4** chooses the collector as the canonical graph-semantic gate, the
compiler calls it directly, and the schema keeps its real job: the runtime
read-boundary validator. It is unchanged. F5 closes as a *decision*, not a rewrite,
and the register/plan/tracker all carry the corrected premise so the stale claim
does not survive in a comment.

## Scope kept

The temptation to "tidy up" the canvas compiler or the schema was declined. The
existing `compileWorkflow` (`compiler.ts:22-72`), the save/update actions, the
whole execution runtime, `workflow.ts`, and `resolver.ts` are all untouched —
`git diff` on the two protected files is empty. This is a new second producer of
`WorkflowDefinition` sitting beside the canvas one, sharing the collector rather
than duplicating it (the plan's explicit "do not create a second DAG validator").

## What is deliberately not implemented

`TYPE_MISMATCH` is still absent, for the same reason as 37.3: every catalogued
output is `z.string()` and no machine-declared cross-field type relationship exists,
so a sound check needs a type-inference layer. Recorded, not faked. It is not part
of this phase's acceptance gate, and no `TYPE_MISMATCH` code was introduced.

## Status: IMPLEMENTED, not VERIFIED — on purpose

The verification gate has two halves: unit tests green, and a production-path check
that the chosen gate runs on materialization. The compiler has **no production
caller until 37.5**, so the second half cannot be met here. The phase is therefore
marked `IMPLEMENTED`, and every document says so plainly rather than borrowing a
`VERIFIED` it has not earned. That check lands when 37.5 wires the compiler into
`generateWorkflow`.
