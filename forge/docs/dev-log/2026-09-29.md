# 2026-09-29 — Agent Task Tool Integration and Agent Runtime Hardening

## Objective

Give the agent a real task-creation capability without weakening the existing
tenant boundary.

Specifically this phase:

1. Gave `ToolExecutor` a trusted `ToolExecutionContext` instead of only
   model-controlled input.
2. Collapsed three independent task-creation implementations into one canonical
   business operation.
3. Replaced the fake `create-task` tool (a renamed `searchKnowledge` stub) with
   a real tool Gemini can actually use.
4. Made the tool usable by having the model supply a human project *name*
   rather than a CUID it cannot invent.
5. Integrated the tool into the registry and documented the behaviour in the
   agent system prompt.

## Architecture Before

Three separate writes, all with different (and mostly missing) authorization:

- `src/app/actions/Tasks/createTask.ts` — `"use server"`. Called `auth()` and
  `getOrgAccess()`, but then wrote with `prisma.task.create`. Also called
  `rateLimit.limit()` **twice**, taking `success` from the first call and
  `remaining`/`reset` from the second, so a single user action consumed the
  budget twice.
- `src/lib/workflow/actions/core/create-task.ts` — wrote with the raw client
  `db.task.create`, with **no** auth and **no** org check. Any `projectId` in
  node config would be accepted, so this path could write a task into another
  organization's project. It also bypassed the CDC.
- `src/app/api/triage/route.ts` — unauthenticated route that wrote
  `prisma.task.create` using a `projectId` taken straight off the request body.

Agent side:

- `ToolExecutor` was `(input: Prisma.JsonValue) => ...`. The tool layer had no
  way to know which organization it was acting for, so any write-capable tool
  would have had to accept `orgId` as model input.
- `src/lib/ai/agent/tools/create-task/` was a byte-identical copy of the
  deleted `search-knowledge` placeholder. It exported `searchKnowledgeTool` /
  `executeSearchKnowledge` and returned an empty result set.
- The registry advertised that fake tool to Gemini.

## Architecture After

```
UI Server Action  (auth, getOrgAccess, rate limit, revalidatePath)
        \
Workflow Action  (task.create, org from persisted Workflow row)
        \
Agent Tool       (executeCreateTask, org from persisted AgentSession row)
        /
        v
createTaskInOrg(input, { orgId, userId? })     <- src/lib/tasks/create-task.ts
        |
        |  validates with shared createTaskSchema
        |  asserts project belongs to trusted orgId
        |  asserts assignee is a member of trusted orgId
        v
extended Prisma client (prisma)
        |
        v
Task row  +  TASK_CREATED CDC (embedding / analytics / email)
```

## Changes Made

### Added

- `src/lib/tasks/create-task.ts` — **the single canonical task creation
  operation.** Exports `createTaskInOrg(input, actor)` and `CreateTaskResult`.
  Worker-safe: no `auth()`, no `notFound()`, no `revalidatePath()`, no `next/*`
  import. Uses the extended `prisma` client so the `TASK_CREATED` CDC fires.
  Returns a discriminated result rather than throwing.
- `src/lib/tasks/projects.ts` — worker-safe, org-scoped project reads:
  `listProjectsInOrg`, `searchProjectsInOrg`, `resolveProjectNameInOrg`.
  Resolution is exact-name first (relying on the existing
  `@@unique([name, orgId])`), then a unique substring match, otherwise reports
  `AMBIGUOUS` with candidates. No function accepts an `orgId` from a model.
- `docs/dev-log/2026-09-29.md` — this file.

### Rewritten (previously the renamed `searchKnowledge` placeholder)

- `src/lib/ai/agent/tools/create-task/schema.ts` — strict Zod schema:
  `title`, `projectName`, `priority?`, `assigneeId?`. No `orgId`, no `userId`,
  no `projectId`.
- `src/lib/ai/agent/tools/create-task/types.ts` — `CreateTaskInput`,
  `CreateTaskOutput`, `CreateTaskProjectSuggestion`.
- `src/lib/ai/agent/tools/create-task/tool.ts` — `createTaskTool`, described as
  a WRITE operation that must only fire on an explicit user request.
- `src/lib/ai/agent/tools/create-task/execute.ts` — `executeCreateTask`.
  Validates input, resolves `projectName` to a project **inside `ctx.orgId`**,
  then calls `createTaskInOrg`. Contains no Prisma code and no task business
  logic. On `PROJECT_NOT_FOUND` / `PROJECT_AMBIGUOUS` it returns real project
  names from the org as `suggestions` so the model can self-correct instead of
  inventing one.
- `src/lib/ai/agent/tools/create-task/index.ts` — barrel re-export.

### Modified

- `src/lib/ai/agent/types.ts` — added `ToolExecutionContext`
  (`{ orgId, userId, executionId }`) and updated the stale comment on
  `AgentToolExecutionEventPayload` that described the old input-only contract.
- `src/lib/ai/agent/tools/registry.ts` — `ToolExecutor` now takes
  `(input, ctx)`. `agentTools` exposes `createTask`; `toolExecutors` maps
  `createTask` to `executeCreateTask`. `searchKnowledge` removed.
- `src/lib/ai/agent/tool-worker.ts` — passes
  `{ orgId: execution.session.orgId, userId: execution.session.userId, executionId: execution.id }`
  from the persisted `AgentSession` row.
- `src/app/actions/Tasks/createTask.ts` — reduced to a thin adapter. Keeps
  `auth()`, the Zod barrier, org resolution, `getOrgAccess()`, `revalidatePath()`
  and the UI response shape. Delegates the write to `createTaskInOrg`. **Fixed
  the double `rateLimit.limit()` call** — now a single call whose result drives
  both the decision and the returned `remaining`/`reset`.
- `src/lib/workflow/actions/core/create-task.ts` — thin worker adapter. Resolves
  the trusted org from the persisted `Workflow` row via `ctx.workflowId` (which
  `wrapper.ts` derives from `stepRun.run.workflowId`), then calls
  `createTaskInOrg`. No longer uses raw `db` for the write, so CDC now fires on
  this path. `ActionResult` contract and `isRetriable` semantics preserved.
- `src/app/api/triage/route.ts` — was a fourth, unauthenticated task write.
  Now requires `auth()`, resolves the project from the request, verifies
  `getOrgAccess()` on the owning org, and creates through `createTaskInOrg`.
  The LLM triage extraction is unchanged.
- `src/core/domain.ts` — added an optional `description` field to the shared
  `createTaskSchema` so the workflow path keeps the description capability it
  had via its old inline write.
- `src/lib/ai/agent/prompts/system-prompt.ts` — added a `<TASK_CREATION>`
  section: createTask is a write, only on explicit request; never choose the
  org; identify projects by name; on `PROJECT_NOT_FOUND`/`PROJECT_AMBIGUOUS`
  use the returned `suggestions` and ask the user; do not report success until
  the tool returns `ok: true`.

### Deleted

- `src/lib/ai/agent/tools/search-knowledge/{execute,index,schema,tool,types}.ts`
  — removed. The registry no longer references them and no source file contains
  the string `searchKnowledge` or `search-knowledge`.

## Security

**Identity sourcing.** `orgId` and `userId` are never model-controlled. The
`createTaskTool` schema is `.strict()` and has no `orgId`/`userId`/`projectId`
field, so the model physically cannot express one.

- Agent path: `tool-worker.ts` reads them from `execution.session.orgId` /
  `execution.session.userId`, loaded by `getToolExecutionForWorker()` from the
  persisted `AgentSession` row. The QStash payload is treated only as a durable
  database pointer.
- UI path: derived from `auth()` plus `getOrgAccess()` on the project's org.
- Workflow path: read from the persisted `Workflow` row via `ctx.workflowId`.
- Triage path: derived from the authorized project + `auth()`.

**Project ownership.** `createTaskInOrg` always asserts

```ts
prisma.project.findFirst({ where: { id: data.projectId, orgId: actor.orgId } })
```

`projectId` is untrusted on all four paths (form input, workflow node config,
resolved project name, request body), so a cross-org `projectId` resolves to
`null` and never reaches the write.

**Assignee membership (new).** `createTaskInOrg` also asserts
`membership.findFirst({ where: { userId: assigneeId, orgId: actor.orgId } })`.
Previously an `assigneeId` was written without any check, which would have
allowed attaching a task to a user outside the organization — reachable once the
agent could supply one.

**CDC.** Only the canonical operation writes a task, and it uses the extended
client. The workflow path previously used raw `db` and silently skipped the
`TASK_CREATED` event; that is fixed.

## Agent Tool

- **Tool name:** `createTask`
- **Input shape:**
  ```json
  {
    "title": "Fix login redirect bug",
    "projectName": "Platform",
    "priority": "HIGH",
    "assigneeId": "<optional cuid>"
  }
  ```
  `title`, `projectName` required; `priority`, `assigneeId` optional. No `orgId`,
  no `userId`, no `projectId`.
- **Executor behaviour:** `executeCreateTask(input, ctx)` parses with the strict
  schema, calls `resolveProjectNameInOrg(ctx.orgId, projectName)`, then calls
  `createTaskInOrg` with `{ orgId: ctx.orgId, userId: ctx.userId }` and the
  resolved project id. Returns `{ type: "json", value: { ok, task?, code?,
  error?, suggestions? } }`. Failures are returned to the model as data rather
  than thrown.
- **Registry integration:** `agentTools.createTask` is passed to
  `generateText({ tools: agentTools })` in `loop-runner.ts`; `getToolExecutor("createTask")`
  resolves to `executeCreateTask` in `tool-worker.ts`. `searchKnowledge` is gone
  from both maps.
  *(Correction 2026-09-29: this line originally said `streamText`. The loop uses
  `generateText`; `streamText` is used by the unrelated RAG chat at
  `src/app/api/chat/route.ts`.)*
- **Project resolution:** `projectName` (not `projectId`) is what the model
  supplies, because `Project` is unique on `[name, orgId]` and a CUID cannot be
  invented reliably. On a miss the tool returns up to 10 real project names from
  `ctx.orgId`.

## Known Remaining Work

- **No write-approval / confirmation gate.** `AgentStatusEvent` has a
  `WAITING_CONFIRMATION` variant, so the architecture anticipates human approval
  for tool calls, but it is not implemented. `createTask` executes as soon as
  the model calls it; there is no approve/reject step. The prompt constrains the
  model, but that is a behavioural guardrail, not an enforcement mechanism.
  Nothing in the dev log or prompt should be read as claiming approval exists.
- **No project context in the prompt.** `buildAgentSystemPrompt` only receives
  `organizationName`; it is not given the user's project list. Disambiguation
  currently relies on the `suggestions` returned by a failed tool call, which
  costs a round trip. Injecting the project list into the prompt builder would
  be the next improvement.
- **No read tools for the agent.** Only a write tool is registered. There is no
  `listProjects` / `listTasks` agent tool, so the agent cannot read state; it can
  only create. The worker-safe helpers in `src/lib/tasks/projects.ts` are already
  in place for those.
- **Task update / status transitions remain unimplemented.** Only creation was in
  scope. `updateTaskSchema` in `src/core/domain.ts` still has no callers, and
  `IN_PROGRESS` / `DONE` are still never written by application code.
- **No unit tests for `createTaskInOrg` or `executeCreateTask`.** The tenant
  boundary is now the single enforcement point for every task write, so it is the
  highest-value place to add tests. None were written in this phase.
- **QStash consumer topology still unverified.** `USE_MULTI_TOPICS = false` sends
  events to topic `"events"`; whether `AGENT_TOOL_EXECUTION_REQUESTED` reaches the
  agent tool route cannot be confirmed from the repository. The agent write path
  is not proven end-to-end at runtime — only at the type and code level.
- **`orgId` is authoritative but the assignee check is a membership lookup.**
  If an org allows guest-style access without a `Membership` row, task
  assignment would be rejected. The current `getOrgAccess` implementation also
  keys on `memberships`, so the two are consistent today.

## Phase 1 — Agent Runtime Hardening

### Objective

Make the existing agent runtime correct, routable, secure, observable and
test-covered. No new capabilities, no architectural rewrite. The `AgentSession`
/ `AgentMessage` / `AgentToolExecution` model, Redis locks, CAS claiming, QStash,
Gemini, the canonical task operation, the trusted `ToolExecutionContext` and the
tool registry are all preserved as-is.

Five concrete defects were fixed:

1. `AGENT_TOOL_EXECUTION_REQUESTED` had no case in the main dispatcher, so with
   `USE_MULTI_TOPICS = false` it was a silent drop.
2. The dispatcher answered every unrecognised event with HTTP 200, which told
   QStash the work was done.
3. The max-step guard was an off-by-one and could not express a terminal
   reason.
4. Nothing stopped Gemini returning two tool calls, and a partial assistant
   message could be persisted before the mismatch was detected.
5. Pusher auth derived the org id from the body with no ownership check, and
   there was no way to re-read a session after a refresh.

### Event routing

`src/app/api/worker/route.ts` now dispatches
`AGENT_TOOL_EXECUTION_REQUESTED` explicitly, and the default branch refuses to
acknowledge work it did not do:

| Condition | Status | Reasoning |
| --- | --- | --- |
| Missing `type` | `400` | Malformed payload. |
| Known `EventTypes` value, no handler | `500` | Misrouting; retrying may fix a transient deploy ordering issue. Must not be a silent drop. |
| Unknown `type` | `400` | Retrying can never help and would burn the retry budget. |

**One consumer per event.** The dedicated
`src/app/api/worker/agent-tool-execution/route.ts` was **deleted**. Keeping it
next to the dispatcher meant two source-level consumers for one event, and that
path could only ever receive traffic from an external QStash consumer that
cannot be verified from the repository. `AGENT_TOOL_EXECUTION_REQUESTED` now has
exactly one consumer, `/api/worker`, which works with `USE_MULTI_TOPICS = false`
and depends on no undocumented external configuration.

> **Operational action required.** If a QStash consumer is currently pointed at
> `/api/worker/agent-tool-execution`, repoint it at `/api/worker`. Until then that
> consumer will 404. The `agent-tool-execution-requested` entry in the
> `topicMap` in `src/lib/events/queue.ts` is now unused, because multi-topic mode
> is off.

### Max steps and terminal reasons

- `AgentSession.terminalReason` (`String?`, indexed) was added, with migration
  `prisma/migrations/20260929120000_agent_session_terminal_reason`. The Prisma
  client was regenerated; the migration has **not** been applied to any live
  database.
- New `AgentTerminalReason` values: `MAX_STEPS_EXCEEDED`,
  `MULTIPLE_TOOL_CALLS`, `NO_TOOL_CALL`, `SESSION_NOT_FOUND`, `ERROR`.
- `AgentStatusEvent` gained explicit `MAX_STEPS_EXCEEDED` and a required
  `reason` on `FAILED`, so a consumer no longer has to parse `errorMessage`
  prose to decide what happened.
- `terminateAgentSessionForMaxSteps` writes `FAILED` +
  `MAX_STEPS_EXCEEDED` with `finalResponse: null`; `completeAgentSession`
  clears `terminalReason`.
- The step gate is now `currentStep > maxSteps` evaluated after the CAS claim,
  so with `MAX_AGENT_STEPS = 5` the model is called exactly five times.

Note that the tool requested on the fifth turn still executes and its result is
persisted; the sixth loop event terminates the session without another model
call. No model call happens after the limit, which is the guarantee that matters,
but the limit is enforced one loop event later than the last model call.

### One tool call per turn

- The installed `ai` package is `6.0.208`, whose `toolChoice` supports only
  `"auto" | "required" | "none" | { toolName }`. It exposes **no**
  `parallelToolCalls` flag, so the provider cannot be asked to disable parallel
  calls through a supported option.
- Enforcement is therefore in `loop-runner.ts`, after `generateText` resolves
  and **before** anything is persisted. The finish reason and tool-call count
  are classified, and a mismatch fails the session with an explicit reason.
  No partial assistant message is ever written, so the transcript can no longer
  contain an assistant turn with two tool calls and no tool results.
- The system prompt was also updated to call at most one tool per turn. The
  prompt is guidance; the runner is the enforcement.

### Pusher authorization

- New `src/lib/pusher/agent-channel.ts` parses the `x-www-form-urlencoded`
  Pusher body and validates the `private-agent-` prefix and a
  `[A-Za-z0-9_-]{1,64}` session id.
- `src/app/api/pusher/auth/route.ts` now requires authentication (`401`
  anonymous), rejects malformed bodies (`400`) and non-conforming channels
  (`403`), and authorizes through `getAgentSessionForUser` — the org id is no
  longer read from the request body. Unknown and foreign sessions are
  indistinguishable to the caller.
- `getAgentSessionForUser` was added to the existing session service because
  NextAuth exposes only `user.id`; authorization is a lookup in that one service
  rather than a second ownership implementation.

### Session recovery

- `GET /api/agent/session/[sessionId]` returns status, current step, final
  response, error, terminal reason, timestamps, messages and tool executions.
  Anonymous `401`, empty id `400`, unknown/foreign `404`.
- Supports `getToolExecutionsForSession` in the tool-execution service.

  `src/lib/pusher/agent-channel.ts`,
  `src/app/api/agent/session/[sessionId]/route.ts`,

- **Modified:** the agent loop worker, loop runner, session service, tool

- `npx jest` — **8 suites, 63 tests, all passing** (52 of them new, across

  `agent-channel`).
- Routing is asserted from the `createWorker` bindings plus live dispatcher

- Static and mock-level only. Pusher, NextAuth, Prisma, Redis and QStash were

### Known remaining work

- **QStash consumer topology is still unverified from the repo.** The routing is
  now correct in source, but whether a deployed consumer points at `/api/worker`
  is an environment fact that must be confirmed before this ships.
- **The migration has not been run.** `terminalReason` will be missing in any
  database that has not had the migration applied.
- **Still a prompt-level guardrail, not a gate.** The single-tool rule and the
  "writes require an explicit request" rule are both enforced by the model
  obeying the prompt. There is still no confirmation step before a write-capable
  tool runs.
- **Still no agent read tools** and no task update/status transitions.
- **No UI.** Nothing subscribes to the agent channel yet, so the Pusher and
  session endpoints currently have no consumer in the app.
- **No durable outbox or reaper.** Terminal transitions still depend on the
  worker running; a crash between the DB write and the Pusher publish leaves the
  UI stale until refresh. `GET /api/agent/session/:id` is the only recovery path.

### What was discovered during the audit

The audit read the implementation rather than the plan, and corrected several
assumptions:

- **`Session GET` and `Secure Pusher auth` are `IMPLEMENTED`, not `PLANNED`.**
  Both were added in the hardening pass above; the planning matrix predated it.
- **There is no client at all.** Nothing in the app calls `POST /api/agent/init`
  or `GET /api/agent/session/[sessionId]`, and nothing subscribes to a
  `private-agent-*` channel or binds `AGENT_STATUS_CHANGE`. The entire agent
  subsystem currently has no UI. The existing `RealtimeListener` and
  `useWorkflowLiveStream` hooks cover the org and workflow channels only.
- **`WAITING_CONFIRMATION` is `DECLARED ONLY`.** The enum value, the status
  event, the `failAgentSession` branch and `cancelAgentSession` all exist — and
  `cancelAgentSession` has **zero callers and can never fire**, because nothing
  anywhere sets a session to that status.
- **The lock TTL is not sized to the model call.** 30 s flat, never renewed. A
  slow `generateText` call can outlive its own mutex. The CAS limits the damage
  but the model call is wasted.
- **The QStash `deduplicationId` does not deduplicate.** It hashes the whole
  CloudEvent including `time` and a `Date.now()`-derived id, so it is unique per
  publish. All real duplicate protection comes from `EventLog(messageId)`.
- **`EventLog` has a residual silent-drop bug.** When the `FAILED → PENDING`
  re-arm CAS loses, execution is skipped and the worker still returns `200` — the
  same class of bug Phase 1 removed from the dispatcher.
- **The tool registry is two literal maps, not one source of truth**, despite
  its own header comment. Nothing checks that `agentTools` and `toolExecutors`
  stay in sync, or that a persisted `toolName` exists in `agentTools`.
- **Two task schemas have diverged.** The domain schema takes `projectId` and
  supports `description`; the tool schema takes `projectName` and has no
  `description`, so **the agent cannot currently set a task description**.
- **Ten dead exports**, listed in the roadmap. Most are harmless, but
  `cancelAgentSession` is *unreachable*, which is easy to misread as "cancel is
  implemented".
- **Two earlier entries in this log were inaccurate** and have been annotated
  in place rather than rewritten: one said `streamText` where the code uses
  `generateText`, and one reported a test count from before the agent suites
  existed.

### Why the task architecture was refactored

Task creation existed as three independent implementations, and the drift was
not theoretical: the workflow node action wrote with the raw Prisma client,
with **no auth and no org check**, so any `projectId` in node config could create
a task in another organization's project — and it skipped the CDC, making the
task invisible to embedding, analytics and email. The UI action called
`rateLimit.limit()` twice per user action, double-spending the budget.

`createTaskInOrg` exists so there is exactly one place where tenant boundaries
are enforced, and therefore exactly one place to audit and test.

### Why trusted tool context was introduced

`ToolExecutor` was originally `(input: Prisma.JsonValue) => ...`, so the tool
layer had no way to know which organization it was acting for. That left one
option for a write-capable tool: **accept `orgId` as model input** — a tenant
isolation hole with a natural-language interface.

`ToolExecutionContext` removes the option. Identity is read from the persisted
`AgentSession` row by the tool worker, so the QStash payload is treated as a
database pointer and nothing more.

### Why project-name resolution exists

`Project` is unique on `@@unique([name, orgId])`, and a human can say a
project's name reliably while a CUID cannot be invented. Beyond usability, an
org-scoped resolver *cannot* return a cross-org project, so it removes the
guess rather than merely checking it afterwards. Ambiguity returns real
candidates and asks the user, because silently picking one would create tasks in
the wrong project.

### Why the agent currently has a small tool surface

One tool. The confirmation gate does not exist yet, so every additional write
tool widens the blast radius of a model mistake. One tool already proves the
whole pipeline end to end, and the org-scoped read helpers needed for Phase 2
already exist.

### What Phase 1 hardening was about

Correctness and honesty of the existing runtime, not new capability: make
routing explicit and singular, make the step budget exact and its reason
machine-readable, make the one-tool rule mechanically enforced rather than
prompt-dependent, stop the dispatcher acknowledging work it did not do, secure
the Pusher channel behind real ownership checks, and add a session recovery
read.

### What Phase 2 will introduce

Confirmation as a separate authorization layer; task read tools (no gate
needed); task update and status tools through domain operations; then
deletion. The session UI, the outbox, the reaper, lock leases, prompt
provenance and the broader testing strategy follow in Phases 3–6.

### What intentionally remains deferred

Parallel tool calls (the architecture is not designed for parallel tool
results, and the one-call rule is what keeps the transcript consistent); model
streaming; dynamic tool loading; multi-provider abstraction; per-organization
prompts; streaming partial tokens through Pusher.

- The task-tool section's verification line reported 3 suites / 11 tests, a

# Phase 2 — Product Capability Layer

## What this phase changed

A write is no longer the model asking for it. It is the model proposing, a row
persisting the proposal, and a human approving it.

**Tool policy.** `AgentToolPolicy` is one field, `access`
(`READ_ONLY` / `WRITE` / `DESTRUCTIVE`), and confirmation is *derived* from it.
The obvious shape — `{ access, requiresConfirmation }` — lets the two disagree
with no type error, and a destructive tool declared `requiresConfirmation:
false` would execute unapproved while looking correctly configured. Deriving it
makes that state unrepresentable.

**One registry.** Tool, executor, policy and proposal renderer register as one
entry. `agentTools` is computed from it, not written out beside it — a
hand-maintained projection would have reintroduced exactly the duplication the
registry exists to remove, and would compile happily when a tool was forgotten.

**Durable confirmation.** `PENDING_CONFIRMATION` and `CANCELLED` states, plus
`confirmedAt` / `cancelledAt`. The loop writes a proposal and stops publishing;
the worker's claim is a CAS from `PENDING` only, so an unapproved or cancelled
row is *structurally* unexecutable rather than guarded by a check someone could
forget.

**Endpoints with no body.** `POST .../executions/[executionId]/confirm` and
`.../cancel` carry only path ids. There is no channel through which substitute
arguments could reach execution, because the executor always reads the persisted
`input` — the same bytes the approval card was rendered from.

**Read and update tools.** `listTasks` (`READ_ONLY`, dispatched immediately)
and `updateTask` (`WRITE`, confirmed), both through canonical domain operations.
`updateTaskInOrg` is the second single enforcement point in the task layer, and
`prisma.task.update` now appears exactly once in `src` — mirroring
`prisma.task.create`. Reads filter through `project: { orgId }` because `Task`
has no `orgId` column, so a query written as `where: { id }` would happily
return another tenant's row.

**Prompt.** `AGENT_PROMPT_VERSION = "v2"`, a `<TOOL_CONTRACT>` section that
explains the pause-for-approval consequence, and `<TASK_UPDATES>`.
`AgentSession.promptVersion` records the contract a session was created under.

**Durability.** Token-guarded Redis lock renewal, an execution liveness
heartbeat, and `reaper.ts` with orphan recovery and stalled-dispatch
redelivery.

## Five defects found and fixed while writing the docs up

These were all live bugs in code written earlier in this phase, found by
re-reading the implementation against its own comments. Each one is a case where
a comment claimed a property the code did not have.

1. **`abandonToolExecution` could not close out a `RUNNING` row.** The worker
   claims `PENDING → RUNNING` and *then* discovers the session is terminal — so
   it called abandon while the row was `RUNNING`, but the CAS only matched
   `PENDING` and `PENDING_CONFIRMATION`. The call silently matched nothing, and
   the row stayed `RUNNING` forever: the event was acknowledged, this worker
   owned the claim, and no reaper sweeps that state. `RUNNING` is now in the
   clause.

2. **The reaper could cancel live work.** Its own comment claimed the CAS from
   `RUNNING` protected "a worker that is merely slow" — it does not. Nothing
   wrote to a `RUNNING` row while the executor ran, so `updatedAt` was pinned at
   the claim and any execution older than the threshold looked identical to a
   dead one. Cancelling it would have killed a side effect that was about to
   succeed and failed the session underneath it — worse than the hang the sweep
   exists to prevent. Fixed with `heartbeatToolExecution` (30 s, CAS on
   `RUNNING`) plus repeating the staleness predicate *inside* the CAS, because
   the read-then-write gap is exactly when a periodic sweep fires.

3. **`failToolExecution` was storing a formatted message, not the stack.** The
   worker passed `error.message` where the service was documented to store
   `error.stack`. The raw error now reaches the service; the session still gets
   the readable message.

4. **Prompt provenance was a lie for legacy rows.** The column defaulted to
   `"v2"`, so every session predating the new contract was stamped as having run
   under it — invisible precisely because the result looks right. The default is
   now the legacy `"v1"`, and `createAgentSession` writes the current version
   explicitly. Separately, the claim "a session keeps the prompt version it was
   created with" was overstated: the prompt is rebuilt every turn, so an old
   session runs the new contract on its next turn. The field is now documented
   as what it is, and the loop logs a warning on divergence.

5. **A repeat confirm reported a phantom error.** `loadConfirmationTarget`
   checked session liveness *before* the execution's own state, so confirming
   an already-completed execution after the session finished returned
   `409 SESSION_NOT_RUNNING` instead of the real answer. Extracted as
   `decideConfirmation`, a pure function where the ordering is testable.

## One test-infrastructure fix

`jest.clearAllMocks()` clears call history but not implementations, so a suite
that stubs `updateMany` leaves that stub in place for every later test. The
first version of the new liveness tests passed for the wrong reason: they ran
against a leftover permissive stub rather than the double's real `where`
filtering. `restorePrismaDouble()` now reinstalls the real implementations, and
the two suites that depend on genuine CAS semantics call it.

# Phase 4 (Assignment 35/36) — Durability and Recovery

## The gap being closed

Phase 2 ended with three named holes, all of the same shape: **the database knew
something the rest of the system would never be told.** A committed domain write
followed by a publish that could fail, recover, and try again; a proposal waiting
for a human who might never come back; and a set of recovery functions that
existed, were tested, and were invoked by nothing at all.

The unifying failure was not "an event is lost". It was that **every recovery
path selected state the failure had already written**. A crashed publish left the
row in a state that said the work was done, so no sweep would ever find it again.

## What changed

**A transactional outbox.** `AgentOutboxEvent`, written by `recordAgentEvent`
inside the caller's transaction. `recordAgentEvent` requires its `tx` argument on
purpose — an outbox writer that could be called outside a transaction is a way to
quietly reintroduce the original bug. `sessionId` and `executionId` are plain
strings with **no** foreign keys, because cascading an owed-work record away with
its session would delete the evidence at the exact moment it mattered.

Delivery is **at-least-once and only at-least-once.** Exactly-once is not
claimed anywhere in the code or the docs. A crash between `publishJSON` and the
`PUBLISHED` mark causes a redelivery, and that is made safe by the consumers'
own compare-and-set — the tool worker claims only `PENDING`, the loop handler only
advances a step it already holds — plus a deterministic `deduplicationId`.

**Approval expiry.** `EXPIRED` is a new terminal state, deliberately *not*
`CANCELLED`: `CANCELLED` means a human declined, and reusing it for a timeout
would feed the model a false account of a user's intent. The `APPROVAL_TIMEOUT`
tool-result also tells it not to achieve the same outcome by another route, which
is the clause that stops it from routing around the gate.

**Scheduling.** `AGENT_MAINTENANCE_REQUESTED` runs all four duties through the
signed `/api/worker` dispatcher, bounded by the payload's `limit`, with a QStash
schedule intended to POST it every five minutes. The schedule does not exist yet —
see the correction below.

**Atomic approval paths.** Confirmation, cancellation and expiry each commit
their transition, their transcript, and their delivery intent in one transaction.

## Two design errors found and corrected mid-implementation

1. **The first outbox claim was not a claim.** It selected `status = PENDING`
   and did not change `status`, so two overlapping maintenance ticks both read
   `PENDING`, both published, and the duplicate was manufactured inside the
   application — the very thing the outbox existed to prevent. The naive fix,
   CAS on `attempts`, is also wrong: an optimistic version check only excludes
   writers that raced *before* the read, and a later batch reads the
   already-incremented value and matches again. The claim now pushes `availableAt`
   forward to a lease deadline and requires the row to still be due against one
   `now` captured per batch — a real CAS on the same field the predicate reads.
   The outbox test was confirmed non-vacuous by temporarily removing the lease
   write and watching it fail.

2. **Expiry was three steps, and the first one was terminal.** The CAS committed
   `EXPIRED` before the transcript and re-arm were written. A crash in that gap
   left a row that `findDueApprovalCandidates` would never select again, and a
   session holding an unanswered tool call with nothing left to recover it. The
   terminal CAS is what made the state unrecoverable, so all three writes now
   share one transaction.

Also corrected: `redeliverStalledConfirmedExecutions` published directly to
QStash, which would have had the sweep doing the dispatcher's job without the
durability. It now re-records intent, which collapses onto the existing row via
the unique `idempotencyKey` and does not reset a delivered one.

## Three security changes that were not really about the agent

- Queue signature verification was skipped when `NODE_ENV === "development"`. An
  environment *name* is not a security boundary: preview and tunnelled processes
  can report it, and the handlers behind it perform real writes with real tool
  inputs. Now `ALLOW_UNSIGNED_LOCAL_WORKER === "true"`, an exact compare —
  a truthiness check would treat `=0` and `=false` as *enabled*.
- The maintenance route had no authentication at all. It briefly required
  `AGENT_MAINTENANCE_SECRET` or `CRON_SECRET`, compared in constant time, and then
  stopped being a route at all: it now runs on the shared worker and inherits
  QStash's per-delivery signing, which verifies a real attestation from the real
  sender instead of comparing a bearer value against a copy of itself.
- QStash delays were cast from `"30s"`-style strings to a number. Every such call
  site type-checked and then failed at runtime. `PublishDelay` is now a template
  literal type converted to QStash's seconds; a bad unit is a compile error.

## One test-infrastructure change

`jest.setup-db-guard.ts` replaces the exported `PrismaClient` with a constructor
that throws, wired through `setupFilesAfterEnv`. A test that constructs a real
client now fails loudly instead of quietly reaching the configured `DATABASE_URL`
— which in this environment is a live Neon primary. Several suites needed
`@/lib/prisma/db` mocked in addition to `@/lib/prisma/extended`.

## Correction: the maintenance schedule is a QStash schedule, and there is not one

The Vercel cron described earlier in this log was replaced, and the replacement is
partly incomplete. Recording it because the failure is the quiet kind.

**What changed.** `/api/cron/agent-maintenance` and `vercel.json` are deleted.
Maintenance is now the `AGENT_MAINTENANCE_REQUESTED` event on the shared signed
worker, triggered by a QStash schedule. The reasons: a Vercel cron is capped at
once a day on Hobby, so the five-minute sweep was plan-dependent; and a static
secret compared against a copy of itself is a weaker boundary than a signature
from the real sender, which QStash already provides for free on the one endpoint
that receives every other event.

**What I checked, and it was not what the source implied.** The QStash account was
queried directly, against the regional endpoint in `QSTASH_URL` rather than the
SDK's default — the default is `eu-central-1` and this account is US East 1, which
is a 404 that reads like a revoked token. Results:

- No `AGENT_MAINTENANCE_REQUESTED` schedule exists in the account.
- The one existing schedule, `CRON_DAILY_DIGEST`, is in `FAIL` state.
- It and the `events` topic both point at a `ngrok-free.dev` tunnel that returns
  `404`. Nothing is serving it.

So the four recovery duties have no caller in any running environment. Every
document written earlier in this log described them as scheduled, and the source
did contain a scheduled-looking cron config, and both were wrong about the running
system. `vercel.json` would have been rejected at build time on a Hobby plan and
would have failed anyway, because the destination did not exist.

**What I deliberately did not do.** `scripts/qstash-maintenance-schedule.mjs`
refuses to create a schedule pointed at `localhost`, plaintext `http://`, or a
temporary tunnel. QStash accepts those without complaint and fails on every tick,
so the result would be a schedule that looks configured, appears in the console,
and never runs. Creating it would have turned a loud, well-documented gap into a
silent one. It exits 1 on the current `APP_URL` and will proceed once a deployed
public origin is set.

**The verify path distinguishes three things,** because conflating them is how the
previous claim went wrong: the schedule exists, the schedule is configured
correctly, and a message was actually delivered. `verify` checks the first two by
reading the schedule back out of QStash and comparing it against the intent, and
reports `delivery: NOT VERIFIED` for the third until a tick has run and QStash
records it. A clean readback is not a delivery.

## Three more defects found while verifying against the real account

1. **Every publish would have 404'd.** `lib/events/queue.ts` built its `Client`
   with no `baseUrl`, so it used the eu-central-1 default against a US East 1
   token. `QSTASH_URL` is now required and passed through. The error is also
   validated *before* the `try` block, because the existing catch rewrites every
   failure to `Failed to queue background job` — which would have buried a missing
   region under an unactionable message and reintroduced the same misdiagnosis in a
   new place.
2. **A schedule body cannot carry a real `id` or `time`.** QStash replays one
   static document forever, so a timestamp written into it is frozen at creation
   time and every tick claims to have happened then. The dispatcher now derives
   both per delivery from the QStash message id and the actual arrival, and an
   explicit `id` still takes precedence so outbox retries keep their identity. The
   script's `verify` fails if a baked-in `id` or `time` ever reappears.
3. **A partial maintenance failure was invisible.** The handler caught every duty
   failure and resolved normally, so the broker recorded the tick as delivered
   while part of the sweep never ran — indistinguishable from a working sweeper,
   which is the exact state the sweep exists to prevent. It now throws *after* all
   four duties settle. Throwing is safe to retry because every duty is idempotent
   and the dispatcher re-arms a `FAILED` `EventLog` row rather than treating it as
   processed; the tests assert both the throw and that the other three duties still
   ran.
