# 2026-09-29 — Agent Task Tool Integration

## Objective

Give the agent a real task-creation capability without weakening the existing
tenant boundary.

Specifically this phase:

1. Gave `ToolExecutor` a trusted `ToolExecutionContext` instead of only
   model-controlled input.
2. Collapsed three independent task-creation implementations into one canonical
   business operation.
3. Replaced the fake `create-task` tool (a renamed `searchKnowledge` stub) with
   a real tool Gemini can actually use.
4. Made the tool usable by having the model supply a human project *name*
   rather than a CUID it cannot invent.
5. Integrated the tool into the registry and documented the behaviour in the
   agent system prompt.

## Architecture Before

Three separate writes, all with different (and mostly missing) authorization:

- `src/app/actions/Tasks/createTask.ts` — `"use server"`. Called `auth()` and
  `getOrgAccess()`, but then wrote with `prisma.task.create`. Also called
  `rateLimit.limit()` **twice**, taking `success` from the first call and
  `remaining`/`reset` from the second, so a single user action consumed the
  budget twice.
- `src/lib/workflow/actions/core/create-task.ts` — wrote with the raw client
  `db.task.create`, with **no** auth and **no** org check. Any `projectId` in
  node config would be accepted, so this path could write a task into another
  organization's project. It also bypassed the CDC.
- `src/app/api/triage/route.ts` — unauthenticated route that wrote
  `prisma.task.create` using a `projectId` taken straight off the request body.

Agent side:

- `ToolExecutor` was `(input: Prisma.JsonValue) => ...`. The tool layer had no
  way to know which organization it was acting for, so any write-capable tool
  would have had to accept `orgId` as model input.
- `src/lib/ai/agent/tools/create-task/` was a byte-identical copy of the
  deleted `search-knowledge` placeholder. It exported `searchKnowledgeTool` /
  `executeSearchKnowledge` and returned an empty result set.
- The registry advertised that fake tool to Gemini.

## Architecture After

```
UI Server Action  (auth, getOrgAccess, rate limit, revalidatePath)
        \
Workflow Action  (task.create, org from persisted Workflow row)
        \
Agent Tool       (executeCreateTask, org from persisted AgentSession row)
        /
        v
createTaskInOrg(input, { orgId, userId? })     <- src/lib/tasks/create-task.ts
        |
        |  validates with shared createTaskSchema
        |  asserts project belongs to trusted orgId
        |  asserts assignee is a member of trusted orgId
        v
extended Prisma client (prisma)
        |
        v
Task row  +  TASK_CREATED CDC (embedding / analytics / email)
```

## Changes Made

### Added

- `src/lib/tasks/create-task.ts` — **the single canonical task creation
  operation.** Exports `createTaskInOrg(input, actor)` and `CreateTaskResult`.
  Worker-safe: no `auth()`, no `notFound()`, no `revalidatePath()`, no `next/*`
  import. Uses the extended `prisma` client so the `TASK_CREATED` CDC fires.
  Returns a discriminated result rather than throwing.
- `src/lib/tasks/projects.ts` — worker-safe, org-scoped project reads:
  `listProjectsInOrg`, `searchProjectsInOrg`, `resolveProjectNameInOrg`.
  Resolution is exact-name first (relying on the existing
  `@@unique([name, orgId])`), then a unique substring match, otherwise reports
  `AMBIGUOUS` with candidates. No function accepts an `orgId` from a model.
- `docs/dev-log/2026-09-29.md` — this file.

### Rewritten (previously the renamed `searchKnowledge` placeholder)

- `src/lib/ai/agent/tools/create-task/schema.ts` — strict Zod schema:
  `title`, `projectName`, `priority?`, `assigneeId?`. No `orgId`, no `userId`,
  no `projectId`.
- `src/lib/ai/agent/tools/create-task/types.ts` — `CreateTaskInput`,
  `CreateTaskOutput`, `CreateTaskProjectSuggestion`.
- `src/lib/ai/agent/tools/create-task/tool.ts` — `createTaskTool`, described as
  a WRITE operation that must only fire on an explicit user request.
- `src/lib/ai/agent/tools/create-task/execute.ts` — `executeCreateTask`.
  Validates input, resolves `projectName` to a project **inside `ctx.orgId`**,
  then calls `createTaskInOrg`. Contains no Prisma code and no task business
  logic. On `PROJECT_NOT_FOUND` / `PROJECT_AMBIGUOUS` it returns real project
  names from the org as `suggestions` so the model can self-correct instead of
  inventing one.
- `src/lib/ai/agent/tools/create-task/index.ts` — barrel re-export.

### Modified

- `src/lib/ai/agent/types.ts` — added `ToolExecutionContext`
  (`{ orgId, userId, executionId }`) and updated the stale comment on
  `AgentToolExecutionEventPayload` that described the old input-only contract.
- `src/lib/ai/agent/tools/registry.ts` — `ToolExecutor` now takes
  `(input, ctx)`. `agentTools` exposes `createTask`; `toolExecutors` maps
  `createTask` to `executeCreateTask`. `searchKnowledge` removed.
- `src/lib/ai/agent/tool-worker.ts` — passes
  `{ orgId: execution.session.orgId, userId: execution.session.userId, executionId: execution.id }`
  from the persisted `AgentSession` row.
- `src/app/actions/Tasks/createTask.ts` — reduced to a thin adapter. Keeps
  `auth()`, the Zod barrier, org resolution, `getOrgAccess()`, `revalidatePath()`
  and the UI response shape. Delegates the write to `createTaskInOrg`. **Fixed
  the double `rateLimit.limit()` call** — now a single call whose result drives
  both the decision and the returned `remaining`/`reset`.
- `src/lib/workflow/actions/core/create-task.ts` — thin worker adapter. Resolves
  the trusted org from the persisted `Workflow` row via `ctx.workflowId` (which
  `wrapper.ts` derives from `stepRun.run.workflowId`), then calls
  `createTaskInOrg`. No longer uses raw `db` for the write, so CDC now fires on
  this path. `ActionResult` contract and `isRetriable` semantics preserved.
- `src/app/api/triage/route.ts` — was a fourth, unauthenticated task write.
  Now requires `auth()`, resolves the project from the request, verifies
  `getOrgAccess()` on the owning org, and creates through `createTaskInOrg`.
  The LLM triage extraction is unchanged.
- `src/core/domain.ts` — added an optional `description` field to the shared
  `createTaskSchema` so the workflow path keeps the description capability it
  had via its old inline write.
- `src/lib/ai/agent/prompts/system-prompt.ts` — added a `<TASK_CREATION>`
  section: createTask is a write, only on explicit request; never choose the
  org; identify projects by name; on `PROJECT_NOT_FOUND`/`PROJECT_AMBIGUOUS`
  use the returned `suggestions` and ask the user; do not report success until
  the tool returns `ok: true`.

### Deleted

- `src/lib/ai/agent/tools/search-knowledge/{execute,index,schema,tool,types}.ts`
  — removed. The registry no longer references them and no source file contains
  the string `searchKnowledge` or `search-knowledge`.

## Security

**Identity sourcing.** `orgId` and `userId` are never model-controlled. The
`createTaskTool` schema is `.strict()` and has no `orgId`/`userId`/`projectId`
field, so the model physically cannot express one.

- Agent path: `tool-worker.ts` reads them from `execution.session.orgId` /
  `execution.session.userId`, loaded by `getToolExecutionForWorker()` from the
  persisted `AgentSession` row. The QStash payload is treated only as a durable
  database pointer.
- UI path: derived from `auth()` plus `getOrgAccess()` on the project's org.
- Workflow path: read from the persisted `Workflow` row via `ctx.workflowId`.
- Triage path: derived from the authorized project + `auth()`.

**Project ownership.** `createTaskInOrg` always asserts

```ts
prisma.project.findFirst({ where: { id: data.projectId, orgId: actor.orgId } })
```

`projectId` is untrusted on all four paths (form input, workflow node config,
resolved project name, request body), so a cross-org `projectId` resolves to
`null` and never reaches the write.

**Assignee membership (new).** `createTaskInOrg` also asserts
`membership.findFirst({ where: { userId: assigneeId, orgId: actor.orgId } })`.
Previously an `assigneeId` was written without any check, which would have
allowed attaching a task to a user outside the organization — reachable once the
agent could supply one.

**CDC.** Only the canonical operation writes a task, and it uses the extended
client. The workflow path previously used raw `db` and silently skipped the
`TASK_CREATED` event; that is fixed.

## Agent Tool

- **Tool name:** `createTask`
- **Input shape:**
  ```json
  {
    "title": "Fix login redirect bug",
    "projectName": "Platform",
    "priority": "HIGH",
    "assigneeId": "<optional cuid>"
  }
  ```
  `title`, `projectName` required; `priority`, `assigneeId` optional. No `orgId`,
  no `userId`, no `projectId`.
- **Executor behaviour:** `executeCreateTask(input, ctx)` parses with the strict
  schema, calls `resolveProjectNameInOrg(ctx.orgId, projectName)`, then calls
  `createTaskInOrg` with `{ orgId: ctx.orgId, userId: ctx.userId }` and the
  resolved project id. Returns `{ type: "json", value: { ok, task?, code?,
  error?, suggestions? } }`. Failures are returned to the model as data rather
  than thrown.
- **Registry integration:** `agentTools.createTask` is passed to
  `streamText({ tools: agentTools })` in `loop-runner.ts`; `getToolExecutor("createTask")`
  resolves to `executeCreateTask` in `tool-worker.ts`. `searchKnowledge` is gone
  from both maps.
- **Project resolution:** `projectName` (not `projectId`) is what the model
  supplies, because `Project` is unique on `[name, orgId]` and a CUID cannot be
  invented reliably. On a miss the tool returns up to 10 real project names from
  `ctx.orgId`.

## Known Remaining Work

- **No write-approval / confirmation gate.** `AgentStatusEvent` has a
  `WAITING_CONFIRMATION` variant, so the architecture anticipates human approval
  for tool calls, but it is not implemented. `createTask` executes as soon as
  the model calls it; there is no approve/reject step. The prompt constrains the
  model, but that is a behavioural guardrail, not an enforcement mechanism.
  Nothing in the dev log or prompt should be read as claiming approval exists.
- **No project context in the prompt.** `buildAgentSystemPrompt` only receives
  `organizationName`; it is not given the user's project list. Disambiguation
  currently relies on the `suggestions` returned by a failed tool call, which
  costs a round trip. Injecting the project list into the prompt builder would
  be the next improvement.
- **No read tools for the agent.** Only a write tool is registered. There is no
  `listProjects` / `listTasks` agent tool, so the agent cannot read state; it can
  only create. The worker-safe helpers in `src/lib/tasks/projects.ts` are already
  in place for those.
- **Task update / status transitions remain unimplemented.** Only creation was in
  scope. `updateTaskSchema` in `src/core/domain.ts` still has no callers, and
  `IN_PROGRESS` / `DONE` are still never written by application code.
- **No unit tests for `createTaskInOrg` or `executeCreateTask`.** The tenant
  boundary is now the single enforcement point for every task write, so it is the
  highest-value place to add tests. None were written in this phase.
- **QStash consumer topology still unverified.** `USE_MULTI_TOPICS = false` sends
  events to topic `"events"`; whether `AGENT_TOOL_EXECUTION_REQUESTED` reaches the
  agent tool route cannot be confirmed from the repository. The agent write path
  is not proven end-to-end at runtime — only at the type and code level.
- **`orgId` is authoritative but the assignee check is a membership lookup.**
  If an org allows guest-style access without a `Membership` row, task
  assignment would be rejected. The current `getOrgAccess` implementation also
  keys on `memberships`, so the two are consistent today.
