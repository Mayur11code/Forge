# 2026-10-12 — Phase 37.5: `generateWorkflow`, and the access decision

37.4 built the compiler and left it with no production caller, on purpose. 37.5
gives it one: `generateWorkflow`, the macro tool that turns a single model-authored
proposal into either a validated proposal or structured validation feedback. It is
the first phase of Assignment 37 where the agent *does* something, so almost all of
the work is deciding precisely how little it is allowed to do.

`src/lib/ai/agent/tools/generate-workflow/` (six files), one registry entry in
`src/lib/ai/agent/tools/registry.ts`, one shared-output helper in
`src/lib/ai/agent/tools/shared-output.ts`, and its 24-test suite. Not yet committed.

## The one-schema decision

The model-facing `inputSchema` is the 37.2 `WorkflowProposalSchema` **by
reference**, re-exported from `schema.ts`:

```ts
export const generateWorkflowSchema = WorkflowProposalSchema;
```

Not a `.extend()`, not a re-declaration. If a tool validates against a copy of the
contract, the copy can drift, and the failure mode is ugly: the model is told its
proposal is well-formed, then rejected by a boundary it cannot see. A test asserts
the two are the same object (`toBe`), so the drift is a test failure, not a
production surprise.

That reference also fixes the division of labour. Structural problems the schema
encodes (missing name, malformed step key, empty `steps`) never reach the executor.
Semantic problems the schema deliberately does not encode — unknown action, dangling
or self dependency, cycle, malformed `{{…}}` reference, missing required input — do,
and come back as issues. The tests pin both halves and assert they stay distinct.

## `READ_ONLY`, and why `WRITE` was wrong

The tracker listed `WRITE` as the "likely candidate" for the policy. It is wrong,
and the reason is the whole point of the phase. `WRITE` gates a confirmation
*before* the executor runs (`policy.ts:52-56` → `requiresToolConfirmation`). But
`generateWorkflow` writes nothing. Confirming it first would mean the user is asked
to approve an artifact that has not been compiled yet, and the model is never shown
the structured `INVALID_INPUT` feedback it needs to self-correct — the tool's entire
output would be withheld behind a prompt. So the policy is `READ_ONLY` (**AD-17**),
the tool runs directly, and the human approval boundary stays where it belongs:
downstream, when a proposal is actually persisted and materialized (37.8/37.9).

The describer is the visible consequence. `describeGenerateWorkflowProposal` exists
because every registered tool satisfies the same optional contract, and
`describeToolProposal` is its only caller today. Because `READ_ONLY` never enters
the confirmation path, the describer is presentation-only and is documented as
such — it is not claimed to be user-visible, and nothing about execution depends on
it.

## Propose only, and prove it

The executor is small on purpose:

```ts
if (input === null) throw new Error("Tool input cannot be null.");
const result = compileWorkflowProposal(input);
if (!result.success) { /* map issues -> shared INVALID_INPUT envelope */ }
return { type: "json", value: { ok: true, proposal: toGeneratedProposal(result.proposal) } };
```

It adds no rules and repairs nothing — the entire validation boundary is 37.4's
compiler. The candidate `WorkflowDefinition` the compiler also produces is
deliberately **not** returned: it carries backend-owned identity that is assigned at
materialization, and a model must not mistake a candidate for a persisted workflow.

The success proposal is content-preserving (name, optional description, step keys,
actions, inputs, dependencies). The failure path reuses the same envelope every tool
uses, via a new `buildStructuredValidationFailure` that shares `failureFromIssues`
with the existing `buildValidationFailure` — so one prompt rule still covers
self-correction across every tool, and each issue arrives with its `path`/`code`/
`message` intact. A `null` payload throws rather than being coerced to
`INVALID_INPUT`: it cannot come from the model (the schema is an object), so it is a
caller bug, and expected-vs-unexpected stays honest.

The side-effect tests are the load-bearing ones for a "propose-only" claim. Spies on
`createTaskAction.execute`, `startWorkflow`, `publishEvent` and `prisma.task.*` are
never called by a valid run; there is no import path from the module to an action
executor, the trigger, the queue or a workflow model. Normal agent infrastructure (a
`ToolExecution` row, the durable tool result, agent events, worker lifecycle) is
expected and unchanged — only workflow-domain effects are prohibited, and none is
reachable. An integration case drives the real `handleToolExecution` path and asserts
a failed proposal is persisted under the exact `toolCallId` with
`AGENT_LOOP_REQUESTED` recorded, so the model can correct it on the next turn.

## Scope kept

The `WRITE` tools' confirmation behaviour is untouched. The 37.2 schema is
untouched. The resolver, canvas compiler, save actions and whole runtime are
untouched (`git diff` empty). No `@ts-ignore`, no unchecked `as`, no suppressions.

One thing is deliberately *not* done: the system prompt still enumerates "exactly
three tools", which is now stale. The tracker marks prompt changes out-of-scope for
37.5 (37.13 owns the prompt text and the version constant), so the text — not the
tool — is what lags. The tool is in `agentTools`; the model can call it.

## A mis-typed line, and why a test caught nothing

While writing the durable-path test, one assertion was left as a nonsense
`value00(value(output))` call — and `npx tsc` passed, because the mock call was typed
`any`. It surfaced only on reading the file back and was rewritten to bind the output
through the JSON-value helper. Worth recording: an `any`-typed mock is a hole in the
type checker exactly where transport correctness matters, and this test leans on a
real integration path rather than the executor's own return type.

## Status: IMPLEMENTED, not VERIFIED — on purpose

The verification gate carries a clause reassigned from 37.2: a proposal produced by
the **real model path** must parse without a compiler fix-up. The mocked/scripted
path is shown to be a single step with no fix-up, but a live model was not called,
and no claim is made that a live model only emits valid proposals. So the clause is
only partially discharged and the phase stays `IMPLEMENTED`. 37.4's own
"production caller" deferral is now satisfied by this phase even though 37.4 itself
was never independently stamped `VERIFIED`.
