# 2026-10-12 — Phase 37.2: the WorkflowProposal contract

Assignment 37.1 gave the model a machine-readable description of every action.
This phase gives it a *contract to author against*: a typed `WorkflowProposal`
that is deliberately not the persisted `WorkflowDefinition`, plus a validator that
resolves every proposed action against the capability catalog and checks each
step's inputs against that action's real schema. It is the schema half of the
"deterministic backend" boundary; the reference half is 37.3.

`src/lib/workflow-types/workflow-proposal.ts`, commit `b28d0e6` (code and tests),
`12c2fb3` (verification docs).

## The proposal is not the definition

The first decision was not to reuse `WorkflowDefinitionSchema`. A proposal is what
a model is allowed to author; a definition is what the backend owns, and conflating
them is how a model ends up able to name fields it must never name.

The differences are all in one direction — the proposal is strictly less than the
definition:

- **`steps` is a `Record<localRef, step>`, not an array.** The key *is* the
  logical step identity, so the local ref a step is referenced by and the ref it
  is keyed under cannot drift, and a duplicate id is unrepresentable rather than
  something a validator has to catch. The definition keeps `id` on the step
  because React Flow needs it there.
- **`inputs`, not `config`,** and validated against the action's real schema
  rather than accepted as `z.record(z.any())`.
- **`dependsOn` is required** (an empty array means "no prerequisite"), matching
  the existing `WorkflowStepSchema`, so a proposal always states its dependencies
  explicitly instead of defaulting them into being.
- **`id`, `kind`, `isCritical`, `routingConditions` and run state are absent.**
  A proposal must not be able to name backend-owned fields (AD-10).

`.strict()` is applied at both levels. An unknown proposal field or an unknown
step field is rejected rather than dropped, so a smuggling attempt fails while the
model is still generating rather than after the workflow is persisted. That is the
same reasoning the issue register used against `z.record(z.any())`: a schema that
silently strips is a schema that did not enforce.

## The local-ref grammar is stricter than the resolver, on purpose

The resolver's path class is `[\w.-]` (`resolver.ts:51`). The proposal's
`PROPOSAL_LOCAL_REF_PATTERN` is `/^[A-Za-z_][A-Za-z0-9_-]*$/` — it excludes the
dot.

That is not an inconsistency with the resolver; it is what makes a step ref safe
to place in front of `.outputs.<field>`. A dot is the path separator, so an id
containing one (`my.step`) could not be referenced unambiguously — `{{my.step.outputs.x}}`
parses as a different path. Braces and whitespace are excluded for the same
reason. The grammar is compatible with the resolver because it is a subset of it,
and a test pins that: every generated id is one the resolver would treat as a
single segment.

## The capability catalog is the only action contract

`validateWorkflowProposal` runs the structural schema, then for each step resolves
`getActionCapability(step.action)` and validates `step.inputs` against
`capability.input`. Two things follow.

**Membership is real.** An action that is not in the 37.1 catalog is
`UNKNOWN_ACTION`, not a step that passes and fails later in the worker. This is
where I4's "action must be a registered workflow action" is actually enforced.

**The capability's own messages and bounds are reused verbatim.** The validator
does not restate `task.create`'s required fields or length limits; it lets the
capability schema reject and maps the Zod issue to a code. The only added rule is
the reference rule below. There is one place that knows what `task.create`
requires, and it is the catalog.

### Forgiveness, and where it stops

A structurally-valid proposal may contain `{{...}}` where a literal is expected —
it is a deferred reference, not a wrong value. So an input issue whose offending
value is a reference template is forgiven: the value is deferred to 37.3, not
rejected here.

The forgiveness is narrow. It applies only to a value that *is* a reference; it
does not apply to **unknown keys**. A reference cannot be smuggled through a field
the action does not declare, because `UNKNOWN_INPUT_FIELD` is raised before the
value is ever inspected. "Forgive the value, never the field" is the whole rule.

## Deliberately not full graph validation

A structurally-valid proposal may reference a step that does not exist. That is
37.3's concern, and rejecting it in the schema would misplace the rule — the
schema cannot see `{{...}}` semantics without becoming the reference validator.
Likewise dependency *existence* and acyclicity are 37.4.

A named test asserts this boundary rather than leaving it implicit: a proposal
with a dangling `dependsOn` and an unresolved `{{...}}` still validates
structurally, and the test says so on the record. The 37.4 compiler composes the
three passes; 37.2 must not pre-empt them.

## Resource bounds, and the hardening that followed

A model response is adversarial input, so the bounds are explicit:

| Bound | Value | Why |
| --- | --- | --- |
| Steps | 50 (`MAX_PROPOSAL_STEPS`) | above any realistic graph and the bounded model loop's `MAX_AGENT_STEPS = 5`, small enough to review and persist as one JSONB value |
| Name / description | 200 / 2000 chars | presentation and prompt budget |
| Serialized size | 256 KiB (`MAX_PROPOSAL_SERIALIZED_LENGTH`) | `task.create.description` is unbounded, so the total needs its own ceiling |
| Input nesting | 8 (`MAX_INPUT_DEPTH`) | every catalogued input is flat today; the resolver walks nested objects, so nesting is allowed but bounded |

The first version was marked `PARTIALLY_VERIFIED` and then the bounds were
hardened, because the failure modes were real:

- **Depth was checked by a recursive walk that ran to completion before
  comparing.** A 50,000-deep payload could exhaust the stack before the limit was
  ever consulted. `exceedsMaxInputDepth` is now an explicit-stack traversal that
  returns the instant a value sits past the limit, so it touches only the nodes
  down to `MAX_INPUT_DEPTH + 1` and cannot overflow. A cycle is caught by the same
  bound, because a cycle necessarily exceeds it.
- **Depth is checked before serialization**, so a deep payload is never
  `JSON.stringify`-ed first — the thing that would have blown the stack was the
  serialization the old order performed.
- **A non-serializable value is a structured issue, not a throw.** A `BigInt`
  input, or a cycle that spans steps, previously produced a thrown `TypeError`.
  `serializeProposal` contains that and returns `INVALID_INPUT` (or
  `INVALID_PROPOSAL_STRUCTURE` for a cross-step cycle), because a validator must
  never throw on the input it is validating.
- **An oversized proposal short-circuits** before per-action validation, so the
  256 KiB ceiling is enforced without doing downstream work first.

Five adversarial cases were added for exactly these paths.

## One clause reassigned, not waived

Phase 37.2's verification gate originally included a clause about a proposal
produced by the *real model path* parsing without a compiler fix-up. No
`generateWorkflow` model path exists at 37.2 — it is 37.5. The clause was
**reassigned to 37.5/37.13**, where that path exists and can be exercised, and
37.5's gate now carries it explicitly. It is relocated, not dropped, and the
tracker records the move rather than letting a green 37.2 imply a model-path proof
it never had.
