# 2026-10-12 — Phase 37.3: the reference validator, and closing F6

This is the phase the whole assignment was aimed at. Everything before it made the
model produce JSON that describes a graph; none of it checked whether the graph
*hangs together*. F6 — missing reference and data-dependency validation — was the
one genuinely new validation in the sequence, and this is where it closes.

`src/lib/workflow-types/workflow-proposal-references.ts` and its 44-test suite,
commits `06fc213` (validator), `69dcfeb` (tests), `4197afb` (docs).

## The defect, stated exactly

The runtime resolver resolves at dispatch time and fails silently. A missing path
becomes `""` inside a larger string, and the literal `{{...}}` text when the
reference is the whole value (`resolver.ts:64-85`). Nothing earlier in the
lifecycle checks that a referenced step exists, that the path is a declared
output, or that the referencing step depends on the referenced one.

So a step may read `{{sibling.outputs.x}}` for a sibling it does not declare in
`dependsOn`. At runtime that resolves to whatever the context happens to hold at
dispatch time — stale from an earlier branch, or absent — and in the absent case
it is the silent-empty-string path. `collectWorkflowDefinitionIssues` cross-checks
`routingConditions` against `dependsOn` (`workflow.ts:190-198`) but never inspects
`inputs`, which is the only field references live in. There was no preflight pass
at all.

## A second reader of the grammar, not a second grammar

The obvious move — export the resolver's parsing and call it — was rejected. Its
parsing is not exported, and re-implementing it *behind an exported boundary* would
either change the resolver's behaviour or duplicate it unsafely. Editing the
resolver was out of scope by the phase's own gate (and by I6's independence: what
generates proposals and what executes them are different concerns).

Instead the new module mirrors the resolver's two patterns verbatim
(`/\{\{([\w.-]+)\}\}/g` and `/^\{\{([\w.-]+)\}\}$/`) and a **parity test** drives
the real exported `resolveInputs` against the same strings. The test asserts the
same tokens resolve, so if the resolver's grammar ever moves, the mirror stops
being a mirror and the suite fails. The resolver is not imported by the validator
and not modified; two tests read it from disk to assert that.

The one thing the validator does that the resolver does not: it treats an
incomplete delimiter as an error. `{{a.outputs.x` (no closer) is left as literal
text by the resolver and surfaces only as wrong runtime data; `extractReferences`
computes the *residue* between tokens and flags any leftover `{{` or `}}` as
`MALFORMED_REFERENCE`. A single stray brace is not flagged — it is not a reference
attempt.

## The rule that was the point: `MISSING_DATA_DEPENDENCY`

The plan's invalid example — a step reading `create_project.outputs.projectId`
while declaring `dependsOn: []` — is rejected outright.

The check is deliberately **direct, not transitive**. If `C` reads `{{A.outputs.x}}`,
then `C` must itself list `A`, even if `C → B → A` would happen to order them. A
chain is not a substitute for a stated dependency, because the whole reason for
requiring the edge is that it must be explicit. A test pins this: a transitive
chain does not satisfy the direct requirement.

A step reading its *own* output is `SELF_REFERENCE`, reported before the
dependency check rather than being mistaken for a satisfied one. And no array is
ever mutated or auto-filled: a data dependency and an execution dependency that
disagree is a rejection, not a repair.

## Ordering in `analyzeReference`, and why

The classification is a fixed sequence, and the sequence is the security model:

1. **structural sanity** — an empty path segment is `MALFORMED_REFERENCE`;
2. **prototype and scope safety before anything else** — `__proto__`,
   `prototype`, `constructor` are `UNSAFE_REFERENCE_PATH`;
3. **source resolution** — a step id, `trigger`, or an out-of-scope namespace;
4. **output-path validity** against the action's declared schema;
5. **the data-dependency rule.**

Step 2 runs before source lookup on purpose: the resolver's traversal is
`current[part]` (`resolver.ts:35`), which follows the prototype chain, so
`{{__proto__.outputs.x}}` must be rejected as a path *before* anyone asks whether
`__proto__` is a step. Referenceable output names come from declared schemas and
never use these segments, so rejecting them cannot reject a legitimate reference.

## Scope: only steps and `trigger`

`RESERVED_REFERENCE_SOURCES` names the runtime namespaces a proposal must not
reach — `user`, `org`, `session`, `tenant`, `db`, `process`, and so on. A source
in that list that is not a proposal step is `UNAVAILABLE_REFERENCE_SCOPE`. The
list is only consulted *after* step lookup fails, so a step legitimately named
`user` still resolves as a step; a test pins that too. Trusted identity is never
made available to the model to make a reference valid (AD-10).

## Output paths are walked against the schema, not a name list

`outputPathExists` walks the capability's Zod output schema rather than comparing
against a flat list of field names. A field is accepted only where the schema
establishes it, and a primitive has no descendants — so
`{{a.outputs.taskId.nested}}` is rejected because `taskId` is a `z.string()`.
`unwrapSchema` peels `.optional()`/`.default()`/`.catch()` wrappers so a wrapped
object still exposes its shape. Every lookup is an own-key check
(`hasOwnProperty`), never `in`, so an inherited member such as `constructor` can
never count as a declared field — belt and braces with the prototype guard above.

Outputs are flat today (`task.create` declares `{ taskId, title }`), but the walk
is written to accept nested outputs if a future action declares them.

## Trigger: fail closed, and say so

There is **no statically-verifiable trigger-output contract**, and rather than
invent one the validator refuses to guess:

- `startWorkflow` primes `trigger.outputs` from `triggerData:
  Record<string, JsonValue>` (`trigger.ts:12,25-29`) — an unconstrained record,
  not a field list.
- `WorkflowProposal` carries no trigger identifier, so no event can be selected.
- `AVAILABLE_TRIGGERS.output` in `registry.ts` is UI presentation keyed by event
  id, not a proposal-addressable contract.

So `STATIC_TRIGGER_OUTPUT_FIELDS` is an intentionally empty allow-list, and any
`{{trigger.outputs.<field>}}` is rejected with `UNKNOWN_OUTPUT`. The trigger is
still special-cased — never treated as an unknown step, never required in
`dependsOn` — but its fields are not invented. If a real contract is declared
later, populating that one constant enables the path without touching the logic.

## What is deliberately not implemented

`TYPE_MISMATCH` is not in the code. A sound type check would need a
type-inference layer: the catalog exposes per-field Zod schemas but no
cross-field relationship metadata, and every catalogued output is `z.string()`
today. Rather than fabricate a check that would be wrong the moment a non-string
output appears, the limitation is recorded in the module header and the phase
record, and no `TYPE_MISMATCH` code was introduced. Dependency existence in
`dependsOn` and cycles remain 37.4.

## What F6's closure rests on

A test that fails when the defect is reintroduced, not a document. The
`MISSING_DATA_DEPENDENCY` test drives the plan's own invalid example and fails if
the check is removed; the parity test fails if the grammar drifts; the
resolver-integrity tests fail if the resolver is touched. The register's F6 row
now reads `CLOSED 2026-10-12` with that evidence attached.

## Still not verified

This is a static preflight. No live execution exercised a generated proposal, and
none could: 37.4 composes this into a compiler boundary, 37.5 generates
proposals, and 37.16 owns the live capstone. The validator's guarantees hold for a
proposal that has already passed `validateWorkflowProposal`; it trusts that
structural boundary and does not re-derive it.
