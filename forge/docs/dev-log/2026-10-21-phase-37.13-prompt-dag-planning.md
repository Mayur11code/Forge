## The rules added (all in `<WORKFLOW_GENERATION>`)

Grouped under four short subsections so the model reads topology, ids, contracts
and boundaries distinctly:

1. **Planning the steps (DAG)** — model each operation as its own step; do not
   serialize independent work; add a `dependsOn` edge only for a genuine
   dependency or output consumption; leave independent operations independent;
   the prompt describes **topology**, and does not claim the engine runs
   independent steps in parallel.
2. **Logical local ids, not database ids** — step ids follow the existing
   `PROPOSAL_LOCAL_REF_PATTERN` grammar and are unique within the proposal;
   `dependsOn` names local ids; never place a UUID/database/persisted entity id
   in a step id or dependency; a local id is not a resource id.
3. **Obey the action contracts** — use only action ids that exist today
   (`task.create` is described as the only one); respect its declared required
   and optional inputs exactly; reference only its declared outputs
   (`taskId`, `title`); never fabricate a real resource id; use the clarification
   contract when one is missing.
4. **References** — use the existing `{{step.outputs.field}}` grammar against a
   real local step and a declared output field; invent no alternative syntax; do
   not put a database id where a step-output reference belongs.
5. **Missing information, criticality, and boundaries** — do not guess missing
   required information; do not own a step's final criticality (a human reviewer
   does, later, and the proposal carries no criticality field); `generateWorkflow`
   proposes but never executes; validation/authorization/approval/materialization
   are the platform's; validation observations are internal correction signals on
   the candidate, not new user intent.

## Version / provenance decision

`v6`. The constant is stamped onto `AgentSession.promptVersion` at creation from
the compiled value by both creation paths (`orchestrator.ts:47` for the real
`POST /api/agent/init` flow, `session-service.ts:57` for `createAgentSession`),
never from a request field. The `init` route's request schema accepts only
`orgSlug` and `message`, so a client cannot claim a prompt version. Existing rows
are never rewritten, so a session created under `v5` keeps `v5`
(`loop-runner.ts:82` warns on a mismatch rather than rejecting). The
`LEGACY_AGENT_PROMPT_VERSION = "v1"` default is untouched for pre-column history.

A new version is provenance, not proof of obedience.
