# 2026-10-20 — 37.6 remediation: a clarification must be able to win

This is a remediation log. It fixes defects found by actually running the
proposal → materialization flow against the live database, not by reading tests.
Three small commits, all `fix(...)`:

- `79efec3` — the projection preview mislabelled approved steps as **Missing Data**,
  and the preview zoom was wrong. (`fix(37.10)`)
- `c7809f2` — unfilled placeholders did not route to the clarification form. (`fix(37.6)`)
- `7bc05a7` — **the real one**: a clarification could not win over a placeholder
  reference on the same field, so the bounded loop retried a value only a human
  can supply until it hit the step cap. (`fix(37.6)`)

The last two are the substance of this log. Both touch surfaces that 37.5/37.6
declared out of scope on purpose (the prompt, the executor's issue precedence),
so the scope decision is recorded below rather than hidden.

## What was actually happening

A session was observed stuck `RUNNING` at step 3/5 with **zero workflow runs**.
The DB showed three `generateWorkflow` executions, all recorded as failures. All
three calls *did* carry `clarifications` — the model asked the right question. It
also wrote `{{clientName}}` / `{{forgeCoreProjectId}}` into those same inputs.

The compiler reported each of those as `UNKNOWN_REFERENCE_SOURCE`. The executor's
gate was, in effect: "any issue that is not `MISSING_REQUIRED_INPUT` is a
model-correctable mistake → return `INVALID_INPUT`." So the clarification was
discarded and the model was told to try again. No retry can invent a human's
value; the loop would have died at `MAX_STEPS_EXCEEDED` (5). The model was being
punished for asking well.

A second, earlier session (`cmvfo40ti…`) reached `COMPLETED` at step 1 with zero
tool calls and a prose question — the v4 prompt did not tell the model to route a
placeholder to the structured clarification field, so no answer surface appeared.

## The two fixes, and why each is where it is

**`c7809f2` — the prompt.** A rule added under `<WORKFLOW_GENERATION>` in
`system-prompt.ts` (and mirrored in the `generateWorkflow` tool description):
when a required input is not present in the conversation, emit a clarification
for it — do not invent a placeholder. `AGENT_PROMPT_VERSION` bumped `v4 → v5`.
This is a prompt change, which 37.5/37.6 explicitly deferred to 37.13. It is
here because the *observable* defect was a missing answer surface, and the honest
minimum that produces the surface is the rule that tells the model to use the
field. The version bump is not cosmetic: sessions record the contract they were
created under (`AgentSession.promptVersion`), and `loop-runner.ts:82` warns on a
mismatch, so the change is attributable in logs.

**`7bc05a7` — the executor.** In `generate-workflow/execute.ts`, an
`UNKNOWN_REFERENCE_SOURCE` issue on an input path that a clarification request
names is now treated as a human-supplied placeholder. It no longer forces
`INVALID_INPUT` and is excluded from the downstream `validateProposalReferences`
re-check. `resolvablePaths = missingPaths ∪ placeholderPaths` is used for the
clarification-legitimacy check. The demotion is deliberately **narrow**: only
`UNKNOWN_REFERENCE_SOURCE` is affected. Malformed references, unknown outputs,
unknown actions, cycles and dangling dependencies still force model correction.

The ordering matters and is the whole point: clarification classification must be
*able* to survive an accompanying soft reference issue, or the cleanest possible
model behaviour (ask, and mark the field) is the behaviour that fails.

## A live session, terminated

A session (`cmvfog8hv…`) was left `RUNNING`, `promptVersion: "v5"`,
`currentStep: 4`, three `COMPLETED` `generateWorkflow` executions, zero workflow
runs, and no pending clarification. Nothing was driving it. It was terminated
through a controlled Prisma write — status `FAILED`, `terminalReason`
`MANUAL_TERMINATION`, with a human-readable `errorMessage` recording why. There is
no session-level terminate route in the app (only per-execution cancel), so this
was a deliberate, recorded operator action, not a code path.

Worth noting for accuracy: an earlier hypothesis that this session was a "v4
zombie" was wrong. The DB says `v5`. The mismatch is a warning, not a hard
reject (`loop-runner.ts:82`). The session was simply orphaned mid-loop, and the
executor fix above is what prevents the next one from arming.

## Honesty note on scope

37.5 and 37.6 both state, in their own documents, *"no prompt change and no
`AGENT_PROMPT_VERSION` bump — deferred to 37.13."* That boundary was crossed
here. It is recorded as a remediation, not silently absorbed: 37.13 still owns
the prompt text and the version constant as a *phase*, but a live-testing defect
in the clarification path could not be fixed without a rule the model reads.
Whether to keep the bump or fold the rule into 37.13 proper is a reviewer call,
and it is flagged as such.

## Live round-trip, after the server restart (2026-10-20)

With the dev server restarted onto v5 + the fixed executor, the previously-stuck
prompt completed the whole chain against the live database:

```text
placeholder prompt
  -> generateWorkflow: clarifications + {{...}} placeholders
  -> NEEDS_USER_INPUT (4 fields)               [previously: INVALID_INPUT -> loop]
  -> human answers (title, two projectIds)
  -> generateWorkflow: ok:true, 2 steps, followup_task dependsOn [kickoff_task]
  -> criticality (followup_task critical, kickoff_task not-critical)
  -> approved -> materialized Workflow
```

New workflow `cmvfs015h…` "Onboard new client": **2 `uiNodes`, 1 `uiEdge`**
(`e:kickoff_task->followup_task`), both nodes `inputsComplete: true` with real
values (the 37.10 "Missing Data" fix holds in the projection). Criticality is
baked into **both** representations — `uiNodes[].data.isCritical` and
`definition.steps[].isCritical` — as `kickoff_task: false`, `followup_task: true`.
`isActive: false`, `eventId: null`; `sourceProposalId` is the durable execution id
under the `@unique` guard; `WorkflowRun` count stayed **0** (no execution). It ran
exactly as designed.

## One thing still not fixed, and it is worth naming

The executor's demotion is `UNKNOWN_REFERENCE_SOURCE`-only. If the model writes a
**plain-string sentinel** — `<Forge Core project id>`, say — into a required
input, `isReferenceTemplate` (`workflow-proposal.ts:293`) does not forgive it,
because that helper matches `{{…}}` only. The capability's `.cuid()` then fails and
the compiler emits `INVALID_INPUT` (`workflow-proposal.ts:427`), which on a
clarified field still forces model correction and can re-arm the loop. This is the
second failure mode observed on the abandoned session's step 2, and this fix does
not cover it. The prompt happens to route every such field through a clarification
(and the model then uses `{{…}}`), so the round-trip above is clean — but the gap
is real and is recorded as a candidate follow-up rather than closed by a silent
widening of the rule. Widening it touches the *classification* rule 37.6 owns, not
the transport, so it deserves its own deliberate change.
