# 2026-10-21 — Phase 37.12 execution handoff (implementation)

**Scope.** Hand a human-approved, materialized `Workflow` to the **existing**
execution engine through an explicit user action, with no second runtime. Also
close the runtime-input trust gap at the handoff entrypoint.

**Status.** `IMPLEMENTED` — **not** `VERIFIED`. No code was staged or committed;
this pass is reported for review.

## What the handoff is

The only run-creation site in the codebase is `startWorkflow`
(`src/lib/workflow/execution/trigger.ts`). Two authorized callers reach it:

1. `triggerWorkflowRun` (`src/app/actions/workflows/workflow-run.ts`) — the
   editor Run control.
2. `POST /api/workflow/test/[workflowId]/test-run` — a currently-unused public
   surface, left hardened and not built upon.

Nothing new was added: no executor, no QStash runner, no lock, no queue, no
migration. The persisted, human-approved definition (steps, dependencies, action
`config`, human-decided `isCritical`) is consumed by the engine as-is; the start
path never writes the `Workflow` row.

## The change: a runtime-input trust boundary (finding I8)

`triggerWorkflowRun` previously accepted an unconstrained
`triggerPayload: Record<string, JsonValue>` that became
`WorkflowRun.context.trigger.outputs`. Two defects:

- **Fabrication.** `WorkflowCanvas` shipped a hardcoded `mockProjectPayload`
  (`{ projectId: 'cmnj8u44p0003a0gcvqgt25dv' }`) — invented runtime data
  unrelated to the workflow being run.
- **Implicit boundary.** A caller could name tenant/identity keys (`orgId`, …)
  in the payload. No authority was actually reachable — `orgId` is server-derived
  from the verified slug — but the boundary relied on the resolver ignoring them.

**Fix.** New pure module `src/lib/workflow/execution/trigger-context.ts`:

- the context is **optional**; a generated, validator-clean workflow supplies
  **none** (it cannot reference `{{trigger.outputs.*}}` —
  `STATIC_TRIGGER_OUTPUT_FIELDS` is empty by design, so those references fail
  closed at proposal time);
- when supplied, it must be a bounded (depth ≤ 8, ≤ 256 values), JSON-only,
  plain-object tree;
- reserved tenant/identity/prototype keys are **refused**, not silently dropped.

The action validates before any run is created; a rejected context returns
`{ success: false, error: "Invalid trigger data." }` and reaches neither the
engine nor the database. `orgId` remains `access.organization.id` — never a
payload value.

`RunWorkflowButton` no longer sends a payload and guards against double-submit
(`submitting` state). This is a UI affordance only — it is **not** server-side
idempotency, and a repeated separate start still creates a second run, which is
the engine's existing, deliberate multiple-run behaviour (preserved, not changed).

## Real vs mocked in the handoff acceptance suite

`src/tests/workflow/execution-handoff.realdb.test.ts` (real PostgreSQL):

- REAL: Prisma/Postgres, `getOrgAccess`, `startWorkflow`, `triggerWorkflowRun`.
- MOCKED: `auth()` (no request/cookie scope in Jest) and `advanceWorkflow` (the
  engine's first domino; letting it run would acquire a real Redis lock and
  publish real QStash messages). The boundary under test is the decision to
  create the run, so the positive case asserts `advanceWorkflow` was reached with
  the created run id.

It accepts a **materialized-shaped** workflow (`eventId: null`, `isActive: false`,
literal-config definition) and asserts: no run exists before an explicit start;
exactly one `RUNNING` run with `context === { trigger: { outputs: {} } }`; the
persisted definition/`updatedAt` unchanged by the handoff; a reserved-key context
creates no run; an unauthenticated caller creates no run.
